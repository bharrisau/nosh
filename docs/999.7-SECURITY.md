# nosh server — OSC accumulation OOM mitigation (post-authentication DoS)

**Phase:** 999.7 (OSC OOM bound — tracked from §7 of 999.1-SECURITY.md)
**Date:** 2026-06-07
**Scope:** Post-authentication PTY output path in `TerminalState::advance` — specifically the OSC accumulation vector described as a residual risk in 999.1-SECURITY.md §7.
**Status:** Mitigated in Phase 19 plan 03. The pre-filter (`OSC_ACCUMULATION_MAX`) bounds vte's internal allocation before it can grow unbounded.

> This is general security-engineering information for the maintainers, not a formal third-party audit. See "Verify before relying on this" at the end.

---

## 1. Threat: unbounded OSC accumulation in vte (post-authentication DoS)

### Root cause

`nosh-server` uses `vte 0.15` with the default `std` feature enabled. Under this feature flag, vte's internal `action_osc_put` handler unconditionally appends bytes to `osc_raw`, an unbounded `Vec<u8>` on the parser (`vte-0.15.0/src/lib.rs:63-64`):

```
// vte 0.15.0, lib.rs (simplified)
fn action_osc_put(&mut self, byte: u8) {
    // Under std feature:
    self.osc_raw.push(byte);  // unbounded
}
```

The existing storage caps — `OSC_52_MAX_BYTES` (64 KiB in `osc52_pending`) and `MAX_TITLE_BYTES` (1 KiB for `title`) — run inside `osc_dispatch`, which fires at `osc_end` only after vte has already buffered the complete sequence. They bound what is *stored* in `TerminalState` fields, not what vte *allocates* while parsing.

### Attack vector

A hostile or buggy application running on the server sends a giant OSC sequence across many `TerminalState::advance()` calls — for example, an OSC 2 window-title sequence with a multi-megabyte payload:

```
ESC ] 2 ; <hundreds of MiB of 'A'> BEL
```

Because `osc_raw` accumulates across calls, each `advance()` call appends its payload to the same growing `Vec<u8>`. On a server hosting multiple sessions, this can exhaust available memory before `osc_end` fires.

### Trust boundary

This vector is reachable **only post-authentication**: PTY output originates from the authenticated user's shell or applications running in their session. It is not reachable from the pre-authentication QUIC ingress path, which is why the 999.1-SECURITY.md §7 analysis correctly scoped this as a separate residual risk (distinct from the pre-auth verdict).

On single-user deployments the practical impact is limited — the attacker is the user. On multi-user servers (multiple simultaneous `nosh-server` sessions sharing one process), a hostile session can OOM the server and disrupt every other user's session. The threat level is therefore higher on shared infrastructure.

### Affected component

`crates/nosh-server/src/terminal.rs` — `TerminalState::advance()` and the underlying `vte::Parser` it feeds.

## 2. Mitigation: 1 MiB pre-bound with parser resync

### Mechanism

A byte-level pre-filter (`osc_prefilter`) is applied to each `bytes` slice before it is fed to `parser.advance()`. The filter maintains shadow state (`in_osc: bool`, `osc_byte_count: usize`) that mirrors vte's private `State::OscString` without accessing vte internals:

- `in_osc` is set true on an OSC start byte (single-byte C1 introducer `0x9D` or the two-byte ESC `]` sequence `0x1B 0x5D`).
- `osc_byte_count` increments for each payload byte while `in_osc` is true.
- `in_osc` is reset to false (and `osc_byte_count` to 0) on OSC terminator bytes: BEL (`0x07`) or String Terminator (`0x1B 0x5C`).

When `osc_byte_count` would exceed `OSC_ACCUMULATION_MAX` (1 MiB = 1 048 576 bytes), the filter returns a strict prefix of `bytes` (truncated at the offending byte). The calling `advance()` method:

1. Feeds only the safe prefix to `parser.advance()`.
2. Replaces `self.parser` with `vte::Parser::default()` (ground state) — this ensures vte does not remain in its internal `OscString` state, which would cause subsequent legitimate bytes to be misinterpreted as OSC payload.
3. Resets `osc_byte_count` and `in_osc` to 0/false so the next `advance()` call starts from a clean slate.

The truncation and parser resync happen **after** feeding the safe prefix (not before) to ensure any OSC payload bytes below the cap are dispatched normally (Pitfall 2 from research notes: resetting before advance discards the safe prefix).

### Key constant

```rust
// crates/nosh-server/src/terminal.rs
pub const OSC_ACCUMULATION_MAX: usize = 1_048_576; // 1 MiB
```

This is the allocation cap — what vte is permitted to buffer in its `osc_raw` field per OSC sequence. It is deliberately larger than the storage caps:

| Constant | Value | Purpose |
|----------|-------|---------|
| `OSC_ACCUMULATION_MAX` | 1 MiB (1 048 576 B) | Allocation cap — bounds what vte buffers per OSC |
| `OSC_52_MAX_BYTES` | 64 KiB (65 536 B) | Storage cap — bounds what is kept in `osc52_pending` |
| `MAX_TITLE_BYTES` | 1 KiB (1 024 B) | Storage cap — bounds what is kept in `title` |

### Overflow behaviour

On overflow, the oversized OSC sequence is discarded silently. The session is **not** killed (D-19-02): a single buggy application emitting a giant title must not terminate the user's live shell session. After the parser resync, subsequent OSC sequences — including OSC 52 clipboard operations and OSC 0/2 title updates — parse and dispatch correctly.

### Integration point

The pre-filter wraps the existing borrow-split pattern:

```rust
pub fn advance(&mut self, bytes: &[u8]) {
    let bytes_to_feed = self.osc_prefilter(bytes);   // ← pre-filter
    let mut parser = std::mem::take(&mut self.parser);
    parser.advance(self, bytes_to_feed);
    if bytes_to_feed.len() < bytes.len() {
        self.parser = vte::Parser::default();          // ← resync on overflow
    } else {
        self.parser = parser;
    }
}
```

The `std::mem::take` borrow-split is preserved unchanged; the pre-filter sits outside it.

## 3. Residual risk and rationale

### Truncation without notification

The oversized OSC is silently dropped. The application's intent (e.g. setting a very long terminal title) is not fulfilled, but there is no feedback mechanism to the application. This is consistent with how terminals handle other out-of-spec sequences. Adding a feedback mechanism would require PTY write-back, which is out of scope and would introduce new attack surface.

### Parser resync edge cases

The resync (`vte::Parser::default()`) returns the parser to ground state. Any bytes between the truncation point and the next valid escape introducer are fed to vte in ground state and handled as normal text or control codes. In practice this means the BEL terminator of the oversized OSC (if it arrives in a later `advance()` call) is treated as a ground-state BEL (a terminal bell, which is benign). No partial OSC dispatch occurs.

### Memory ceiling

The worst-case per-call allocation by vte is approximately `OSC_ACCUMULATION_MAX` bytes (1 MiB) per active OSC sequence. A session with one active OSC at any time uses at most 1 MiB of vte-internal heap in addition to the base `TerminalState` allocation. Across N sessions, the ceiling is N × 1 MiB for OSC accumulation alone.

## 4. Regression test reference

The regression test added in Phase 19 plan 03 (`terminal.rs` test module) directly exercises this mitigation:

**Test:** `oversized_multi_chunk_osc_is_bounded_then_resyncs`

The test:
1. Feeds a 10 MiB OSC 2 title sequence to `TerminalState::advance()` in 4 096-byte chunks (~2 560 calls).
2. Asserts the title field is not 10 MiB (either `None` or bounded by `MAX_TITLE_BYTES`).
3. Feeds a normal OSC 2 title (`"OK"`) and asserts it is stored correctly — proving parser resync worked.
4. Feeds an OSC 52 clipboard sequence and asserts it dispatches correctly — proving the full OSC path is functional after resync.

Before the mitigation, this test would exhaust available memory (or be killed by the OS) before any assertion ran. After the mitigation, it completes in approximately 1 second with all assertions passing.

**Fuzz target:** `fuzz/fuzz_targets/osc_accumulation.rs` also drives a deterministic 10 MiB multi-chunk OSC sequence in addition to its existing libFuzzer corpus path. The `OSC_ACCUMULATION_MAX` constant is imported and checked in both paths.

## 5. Related constants and caps retained

The following storage caps from Phase 16 are retained unchanged and continue to apply after the accumulation pre-bound:

- `OSC_52_MAX_BYTES` (65 536): OSC 52 data is truncated to this cap in `osc_dispatch` before storing in `osc52_pending`. This prevents oversized clipboard payloads from consuming excessive heap in the stored state.
- `MAX_TITLE_BYTES` (1 024): OSC 0/2 title strings exceeding this cap are silently discarded in `osc_dispatch`. This prevents unbounded `title` field growth.

The accumulation pre-bound (`OSC_ACCUMULATION_MAX`) and the storage caps are complementary and independent:

- The accumulation pre-bound protects vte's internal parse buffer from growing unbounded.
- The storage caps protect `TerminalState` fields from growing unbounded after dispatch.

Both layers are necessary. Without the accumulation pre-bound, a multi-chunk OSC exhausts memory before `osc_dispatch` is called and the storage caps can act.

## Verify before relying on this

- The memory-bound figure (`OSC_ACCUMULATION_MAX = 1 048 576` bytes) and the resync behaviour should be re-confirmed if `vte` is upgraded to a version with a different `osc_raw` buffering strategy. The pre-filter shadow-state logic (`in_osc` / `osc_byte_count`) mirrors vte's private `State::OscString` transitions; a vte refactor could affect correctness.
- Re-run `cargo test -p nosh-server --lib terminal::` after any vte upgrade to confirm `oversized_multi_chunk_osc_is_bounded_then_resyncs` and the broader OSC test suite still pass.
- The fuzz target (`osc_accumulation`) provides ongoing regression coverage; re-run `cargo +nightly fuzz run osc_accumulation` periodically and after any vte or `TerminalState::advance` change.
- This mitigation applies only to the server-side terminal model. If a future architecture places OSC parsing in the client or in a shared library, the pre-filter must be applied there as well.
