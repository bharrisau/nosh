# nosh server — pre-authentication attack-surface security review

**Phase:** 999.1 (Server attack-surface hardening — expose-to-internet readiness)
**Date:** 2026-06-07
**Scope:** everything reachable on the server's UDP/443 QUIC ingress **before and during authentication** — the QUIC packet path (delegated to `quinn`/`quinn-proto`), the nosh wire decoders, and the half-open connection resource bounds.
**Verdict:** no panics, OOMs, or unbounded growth observed on hostile input across a multi-hour fuzzing campaign (zero crash artifacts). One transitive-dependency advisory (RUSTSEC-2023-0071) is documented as an accepted residual risk. The pre-auth surface is assessed as safe to expose **raw on UDP/443**, subject to the residual risks and verification steps below.

> This is general security-engineering information for the maintainers, not a formal third-party audit. See "Verify before relying on this" at the end. A QUIC-terminating HTTP/3 reverse proxy is a *different* topology and is out of scope here (see Residual risks).

---

## 1. Pre-auth memory & connection caps

Unauthenticated/half-open connection state is explicitly bounded (`crates/nosh-server/src/server.rs`):

- **Half-open cap:** `AuthLimits { max_concurrent: 64, auth_timeout: 5s }` (`server.rs:35-48`). A `tokio::Semaphore` (`server.rs:133`) caps concurrent *pre-auth* handshakes at 64; excess incoming connections are refused (`incoming.refuse()`), and the permit is released the moment the handshake resolves (success, failure, or timeout) so authenticated sessions never consume pre-auth capacity.
- **Auth-completion timeout:** 5s — a connection that does not complete the SSH-key handshake is dropped, bounding how long a half-open connection can hold a permit.
- **Datagram buffers:** 1 MiB receive + 1 MiB send (`crates/nosh-proto/src/transport.rs`), and a finite **300s idle timeout** (never infinite).
- **Worst-case pre-auth memory:** ≈ 64 × ~2 MiB datagram buffers ≈ **128 MiB**, plus quinn's per-connection transport state. Half-open connections do not negotiate full datagram buffers, so this is an upper bound.

**Residual unknown (A7):** quinn's exact per-half-open-connection allocation is not exposed in its public API; the 64-permit cap bounds the *count*, which is the controlling factor.

## 2. Amplification posture (spoofed-source packets)

Verified against `quinn-proto 0.11.14` source (the version in `Cargo.lock`):

- **A1 — `migration(true)` does NOT weaken pre-handshake anti-amplification.** The 3× limit is enforced purely on path validation state and byte counters in `anti_amplification_blocked()` (`quinn-proto-0.11.14/src/connection/paths.rs:153-155`) with no reference to the migration flag. The migration flag is consulted only in `remote_may_migrate()` (`connection/mod.rs:3782-3787`), which applies **only post-handshake** to packets from a new address. `ServerConfig` defaults to `migration: true` (`config/mod.rs:244`); our explicit `migration(true)` documents that default and has no pre-auth security impact.
- **A2 — quinn issues no Retry by default; the RFC 9000 §8.1 3× limit is the sole pre-handshake anti-amplification mechanism.** `handle_first_packet()` (`endpoint.rs:500-514`) raises a new connection for the application to accept/refuse/retry; it does not call `self.retry()` internally. `retry()` (`endpoint.rs:721-768`) is a caller-invoked API we do not currently use; a token-less Initial yields `IncomingToken { validated: false }` (`token.rs:116-129`) with no library-issued Retry.

**Recommended optional hardening:** calling `Incoming::retry()` in the accept loop would add address validation (a stronger anti-amplification + spoof-resistance guarantee) before committing connection state. Not currently implemented; low priority given the 3× limit + the 64-permit half-open cap.

## 3. Pre-auth resource exhaustion

The connection-flood path has a behavioural regression baseline: `preauth_flood_bounded` (`crates/nosh-client/tests/auth.rs`) drives a junk-sender flood and asserts a legitimate client still connects and runs a session — i.e. the half-open cap + auth timeout prevent a pre-auth flood from denying service to real clients. `mutual_auth_inprocess_happy_path` corroborates the happy path is unaffected. Both pass.

## 4. Fuzzing results

Coverage-guided fuzzing (`cargo-fuzz` / libFuzzer, nightly; harnesses in `fuzz/`). All decoders are pure `&[u8]` → `Result` functions; the QUIC harness drives `quinn-proto`'s sans-IO `Endpoint::handle` in-process with a deterministic seed. Campaign ran across several sessions on 2026-06-06/07 (adaptive core reallocation: cores were shifted off saturated targets onto the slowest, `quic_packet`, for the final ~9h).

**Zero crash artifacts across all targets** (no panic, no OOM at the 2048 MiB libFuzzer RSS cap, no timeout).

| Target | What it fuzzes | Peak executions | Coverage / features | Corpus | Crashes |
|--------|----------------|----------------:|---------------------|-------:|:-------:|
| `quic_packet` | `quinn-proto Endpoint::handle` (malformed/oversized/truncated UDP) | ~875 M | cov 1174 / ft 1642 | 2,897 | 0 |
| `osc_accumulation` | `TerminalState::advance` OSC/title caps | ~15 M¹ | cov 896 / ft 6023 | 142,884 | 0 |
| `codec_decode` | reliable-stream `Message` postcard decode | ~838 M | saturated (cov 423 / ft 893) | 7,089 | 0 |
| `decode_datagram` | datagram `StateDiff`/`DiffRun` | ~643 M | saturated (cov 253 / ft 688) | 1,298 | 0 |
| `read_message` | 4-byte length-prefixed framing (`MAX_FRAME_LEN` 16 MiB) | ~94 M | saturated (cov 590 / ft 982) | 1,811 | 0 |
| `decode_epoch_ack` | `ClientEpoch` (tag 0x02; rejects 0x01) | ~2.1 B | saturated (cov 74 / ft 75) | 27 | 0 |

¹ `osc_accumulation` has a far lower exec rate because each input runs the full VT/terminal state machine; its 143k-entry corpus and stable feature count are the saturation signal.

All targets reached coverage saturation (feature counts flat for hours) under these execution counts with no crashes — the campaign was stopped at convergence. Decoder tag checks and the `read_message` length-prefix guard held against arbitrary bytes.

> **Caveat — `osc_accumulation` is false confidence for one DoS path.** libFuzzer's default `max_len` (4096) produces inputs far too short to reach vte's *unbounded pre-dispatch* OSC buffer (see §7, **OSC-OOM**). Its "0 crashes" therefore does **not** clear that path. It IS reachable only post-authentication (PTY output), so it does not affect the pre-auth verdict — but it is a real, separately-tracked finding (phase 999.7). A proper test needs a multi-chunk OSC far larger than 4096 bytes.

## 5. Dependency advisory scan (cargo-audit)

A `cargo audit` job (`actions-rust-lang/audit@v1`) was added to `.github/workflows/ci.yml` (`audit` job) to scan `Cargo.lock` against the RustSec DB on every push/PR. One advisory surfaced:

- **RUSTSEC-2023-0071 — Marvin timing attack on `rsa 0.9.10`** (transitive via `ssh-key 0.6.7` → `nosh-auth`). **No fixed version available upstream.** See §7 for disposition.

## 7. Residual risks (accepted)

- **OSC-OOM — unbounded OSC accumulation (post-auth DoS), tracked as phase 999.7.** `nosh-server` uses `vte 0.15` with the default `std` feature, where vte's internal `osc_raw` is an **unbounded `Vec<u8>`** (`vte-0.15.0/src/lib.rs:63-64`); `action_osc_put` only bounds it under `not(feature="std")` (`lib.rs:544-552`). Our `OSC_52_MAX_BYTES`/`MAX_TITLE_BYTES` caps run in `osc_dispatch`, which fires at `osc_end` — **after** vte has already buffered the whole sequence. A long OSC string in PTY output (e.g. `ESC]52;c;<hundreds of MB>`), delivered across many `TerminalState::advance` calls, grows vte's buffer until OOM. **The Phase-16 mitigation reasoning was incorrect** — it assumed the buffer was bounded by the OS pipe-buffer size, but `osc_raw` accumulates *across* reads, not per read. Reachable only **post-authentication** (it is PTY output, not pre-auth ingress), so it does **not** affect the pre-auth "safe to expose" verdict — but it is a genuine availability DoS, worse on shared/multi-user servers (the terminal model lives in the shared server process). Fix tracked as **phase 999.7** (bound OSC accumulation before vte, with a multi-chunk adversarial test).
- **RUSTSEC-2023-0071 (`rsa 0.9.10`)** — the Marvin attack is a timing side-channel on RSA *decryption*. nosh uses `rsa` (via `ssh-key`) only for **parsing** RSA public keys from `authorized_keys`/`known_hosts`, not for decryption operations, so the side-channel is not exercised on the server's hot path. No upstream fix exists. **Disposition: accepted residual.** Re-evaluate if `ssh-key`/`rsa` ships a patched release, or consider restricting to Ed25519/ECDSA identities.
- **quinn per-connection allocation (A7)** — not publicly quantified; bounded in count by the 64-permit half-open cap.
- **Optional Retry/address-validation hardening** — not implemented (see §2); the 3× limit is the current pre-handshake protection.
- **HTTP/3 reverse-proxy topology is out of scope and NOT covered.** A QUIC-terminating proxy ends the connection at the proxy, breaking end-to-end mutual auth and migration; the design's answer is WebTransport-over-HTTP/3 with an inner SSH-key handshake (milestone M7, not built). This review hardens the *raw* UDP/443 ingress and the inner-handshake decoders that would also sit behind such a tunnel.
- **Client trust-boundary (malicious server)** is a separate concern (backlog 999.2), not covered here.

## Verify before relying on this

- Confirm the GitHub Actions **`audit` job is green** after pushing (it could not be verified from the dev sandbox).
- The fuzz corpora are committed under `fuzz/corpus/`; re-run `cargo +nightly fuzz run <target>` periodically (and after any decoder / `quinn` change) to catch regressions — a short CI fuzz job was deliberately not added (operator decision D-03).
- Re-run `cargo audit` / `cargo deny check` on dependency bumps; revisit RUSTSEC-2023-0071 when an `rsa` fix lands.
- This assessment covers raw UDP/443 exposure only; the reverse-proxy/WebTransport path needs its own review when M7 is built.
