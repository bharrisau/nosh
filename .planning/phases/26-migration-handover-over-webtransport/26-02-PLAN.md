<objective>
Prove SC#2 / MH-2 over a real WebTransport connection: two clients presenting the same
reattach token concurrently resolve atomically to exactly one active session, with the
loser receiving `ReattachErr`. The guard (`SessionRegistry::reattach` atomic
`Orphaned → Reconnecting` under the registry lock) is already implemented and covered by
three registry unit tests (RESEARCH.md §"MH-2 Guard Status"). This plan adds the missing
integration-level proof that the guard holds across two concurrent real WT connections,
not just in-process registry calls.

Purpose: SC#2 is a load-bearing safety property — a double-attach race would let two
clients drive one PTY. The unit tests prove the registry state machine; this test proves
the property survives the full WT path (inner auth on each connection + Reattach on the
authenticated stream + the server's reattach handler). It is adversarial: it must fail if
the `state != Orphaned → NotOrphaned` check were removed from the registry.

Output: a new `wt_concurrent_reattach.rs` integration test under the `webtransport`
feature.
</objective>

    Establish then orphan a real WT session, then race two concurrent reattach attempts with the SAME token:
    1. Build the real-auth WT harness per the inner_auth.rs pattern: host + client keypairs, `authorized = vec![client_key]`, `known_hosts_trusting`, `spawn_wt_server_real_auth(Some(SH), authorized, host_signer)`. Keep `server.cert_hash`, `server.addr`, and (for diagnostics) `server.registry`.

FIRST attach: `connect_wt` → `run_inner_auth_client` → on the authenticated stream `open_session_with_token`-equivalent: send `SessionOpen` and read `SessionOpened { token }` to capture the token. Then DROP this first transport to orphan the slot (so a reattach is permitted — Reattach on an Active slot is the *other* test in reattach.rs; MH-2 here is two reattaches racing for the orphaned slot). Wait (bounded) until the slot is Orphaned (poll registry if a public query exists, else bounded ~300ms sleep with a server.rs:1500 comment).
    3. RACE: build TWO fresh client connections concurrently. For each: `connect_wt` (fresh config from `server.cert_hash`) → `run_inner_auth_client` (use `client_signer.clone()` — both attempts present the SAME identity and SAME token, which is the realistic double-attach case) → `send_reattach(send, token, 0)` → `await_reattach_reply(recv)`. Launch both as concurrent tasks (`tokio::join!` of two async blocks, or two `tokio::spawn` joined) so they genuinely race the registry lock. Each returns its `ReattachOutcome`.
    4. ASSERT (adversarial core — must fail if the guard regressed):
       - Exactly one outcome is `ReattachOutcome::Ok` and exactly one is `ReattachOutcome::Err`. Compute `ok_count` and `err_count` over the two results and assert `ok_count == 1 && err_count == 1`. (If the `state != Orphaned` guard were removed, BOTH could be Ok → this assertion fails, which is the point.)
       - Do NOT assert WHICH connection wins (the race is nondeterministic) — only that exactly one does.
       - Do not print the token (D-07).
    Wrap every cross-network await in `tokio::time::timeout` (~10s) so a hang fails fast. Note in a comment that this exercises the same atomic `Orphaned → Reconnecting` guard the registry unit tests cover (registry.rs:708-718), now over two concurrent real WT connections.
