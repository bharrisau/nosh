<objective>
Make the server serve scrollback. Flip the `ChannelType::Scrollback` accept gate from reject to accept in both the fresh-session and reattach-session pumps, and add a dedicated `run_scrollback_sender_task` that reads `ScrollbackRequest` from the channel's own RecvStream, snapshots scrollback lines + the live epoch atomically, and writes `ScrollbackPage` frames over a reliable SendStream paced by byte credit.

Purpose: This is the server half of SCROLL-01/02/05. It must obey the locked security invariants: reliable-only at the type level (S-1), separate task with bounded mpsc drop-oldest (M-6/S-4), atomic epoch capture (S-5), and request on the channel data stream not control (M-2).
Output: A new production `run_scrollback_sender_task` in channel.rs and the accept+spawn wiring in server.rs (both session paths).
</objective>

    Loop structure mirrors run_echo_loop's credit-pause idiom: maintain `let mut remaining_credit: u64 = INITIAL_CREDIT;`. When `remaining_credit == 0`, block on `events.recv()` and only handle `ChannelEvent::Credit(n)` (saturating_add) / `Close`/None (break); `continue`.
    Otherwise `tokio::select!` on (a) decoding the next `ScrollbackRequest` from `ch_recv` via `nosh_proto::codec::read_message` and (b) `events.recv()` for Credit/Close. On a decoded `Message::ScrollbackRequest { from_line, count, .. }`: clamp `let count = (count as usize).min(MAX_PAGE_SIZE);`. Capture the epoch FIRST into a local — start from `initial_epoch`, or read the pump-updated epoch source (see action note below) — then enter `slot.with_terminal_state(|ts| ts.scrollback_lines(from_line, count))` to get `(lines, total_available)`. Because the closure is synchronous, the captured epoch and the lines are mutually consistent (S-5). Build `Message::ScrollbackPage { channel_id, from_line, total_available, epoch_at_snapshot, lines: <ScrollbackLine vec from lines> }`, encode it, deduct `encoded.len() as u64` from `remaining_credit` (saturating), and write to `ch_send` only while `remaining_credit > 0` (pause before writing if the encoded page exceeds remaining credit — wait for a Credit event first). Decode any non-ScrollbackRequest frame as a no-op (ignore). Never write to the control stream directly — route `ChannelClose` via `control_tx` (A4 invariant).
    Epoch source: per RESEARCH Open Question 2, the cleanest is for the pump to share the live epoch via an `Arc<std::sync::atomic::AtomicU64>` that the pump updates each diff tick; the task reads it with `Ordering::Acquire` immediately before entering `with_terminal_state`. Document the S-5 rationale in a comment.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → server scrollback channel (ch_recv) | untrusted ScrollbackRequest{from_line,count} crosses into server allocation + index arithmetic |
| scrollback sender task → client (ch_send) | server must guarantee reliable in-order delivery; must never use datagrams |
| pump select! loop ↔ scrollback sender task | the sender must not block the pump (PTY latency / diff tick isolation) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-05 | Information disclosure / Tampering | scrollback over datagrams (S-1) | mitigate | `run_scrollback_sender_task` signature takes `&mut SendStream` only, no `&Connection`; acceptance grep proves no `send_datagram` token in the function body |
| T-22-06 | Denial of service | sender blocking the pump (M-6) | mitigate | separate `tokio::spawn` task; bounded `mpsc(64)`; any pump-side push uses `try_send` + drop-oldest, never `.await` in a select! arm |
| T-22-07 | Tampering | torn epoch/scrollback read (S-5) | mitigate | epoch read into a local from `epoch_src` (Acquire) immediately before the synchronous `with_terminal_state` closure — no `.await` between them, so epoch and lines are consistent |
