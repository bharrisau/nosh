## Summary

This phase has four concrete deliverables: (1) a `fuzz/` cargo-fuzz crate with coverage-guided fuzz targets for every untrusted decoder in `nosh-proto`; (2) a raw QUIC-packet fuzzer exercising the `quinn-proto` `Endpoint::handle` sans-IO path; (3) `cargo audit` added to CI; and (4) a written residual-risk security document.

The good news: the existing decoder code is already well-structured for fuzzing. All five targets (`decode`, `read_message`, `decode_datagram`, `decode_epoch_ack`, OSC accumulation via `TerminalState::advance`) are pure or near-pure functions over `&[u8]`. The `arbitrary` crate (1.4.2 on the registry; not yet in `Cargo.lock`) lets the fuzz harness derive structured inputs for postcard-typed fuzzing. The only async target (`read_message`) needs a thin `tokio::runtime::Runtime::block_on` or `std::io::Cursor` wrapper.

The QUIC-packet fuzzer is the most interesting research item. `quinn-proto 0.11.14` exposes a clean sans-IO `Endpoint::handle(now, remote, local_ip, ecn, data, buf)` API that accepts raw `BytesMut` and returns a `DatagramEvent` (or `None`). This is deterministic and I/O-free — exactly what a fuzz target needs. The fuzz crate can construct a minimal in-process server `Endpoint` using `EndpointConfig::default()` + the same `rustls::ServerConfig` path already used by `build_server_config()` (ephemeral self-signed cert + `AuthorizedKeysVerifier`), feed arbitrary bytes into it, and assert it does not panic. Our own config misuse and amplification posture are what we are testing; quinn-proto internals are treated as a maintained black box.

Amplification posture: quinn enforces the QUIC RFC 9000 §8.1 3× anti-amplification limit on all connections until the client address is validated via the TLS handshake (or a Retry). Our config does NOT call any form of `use_retry` / `require_address_validation` override — the default behaviour is to apply the 3× limit before handshake completion. Connection migration (`server_config.migration(true)`) only activates after a validated connection, so it does not weaken the pre-auth limit. [ASSUMED: that migration(true) does not change the initial anti-amplification posture — verify via quinn-proto source or docs at implementation time.]

**Primary recommendation:** Use the quinn-proto `Endpoint::handle` sans-IO path for the QUIC-packet fuzzer. Do not use a raw UDP socket send to a running server in a separate process — it adds network latency, non-determinism, and process management complexity that make it unsuitable for a fuzzer.

## Architecture Patterns

### Recommended `fuzz/` Layout

cargo-fuzz convention: the `fuzz/` directory lives at the workspace root and is EXCLUDED from the workspace so `cargo test --workspace` never tries to build or run it (fuzz targets are `#[no_main]` binaries incompatible with the test runner).

```
nosh/
├── Cargo.toml            ← add exclude = ["fuzz"] under [workspace]
├── Cargo.lock
├── fuzz/
│   ├── Cargo.toml        ← generated by cargo-fuzz; name = "nosh-fuzz"; publish = false
│   ├── Cargo.lock        ← separate lock for fuzz crate (cargo-fuzz manages this)
│   ├── fuzz_targets/
│   │   ├── codec_decode.rs
│   │   ├── read_message.rs
│   │   ├── decode_datagram.rs
│   │   ├── decode_epoch_ack.rs
│   │   └── osc_accumulation.rs
│   │   └── quic_packet.rs
│   └── corpus/
│       ├── codec_decode/       ← hand-crafted seed inputs (valid postcard frames)
│       ├── read_message/       ← 4-byte length prefix + body seeds
│       ├── decode_datagram/    ← 0x01 tag + valid postcard StateDiff seeds
│       ├── decode_epoch_ack/   ← 0x02 tag + varint body seeds
│       ├── osc_accumulation/   ← VT byte sequences starting with ESC ] ...
│       └── quic_packet/        ← QUIC Initial packet header seeds
└── crates/
    ├── nosh-proto/
    └── nosh-server/
```

**Workspace exclusion** — add to root `Cargo.toml` under `[workspace]`:
```toml
exclude = ["fuzz"]
```

This is the standard cargo-fuzz pattern. The fuzz crate has its own `[workspace]` block (cargo-fuzz generates it with `[package.metadata] cargo-fuzz = true`) so it is self-contained. [CITED: cargo-fuzz README / rust-fuzz.github.io/book]

### Pattern 1: Pure-function fuzz target (bytes)

```rust
// fuzz_targets/codec_decode.rs
#![no_main]
use libfuzzer_sys::fuzz_target;
use nosh_proto::codec;

fuzz_target!(|data: &[u8]| {
    // codec::decode takes the postcard body (no length prefix).
    // Invariant: arbitrary input → Ok or Err, NEVER panic.
    let _ = codec::decode(data);
});
```

[CITED: rust-fuzz.github.io/book/cargo-fuzz/tutorial.html — basic fuzz_target! shape]

### Pattern 2: Async fuzz target (read_message with in-memory reader)

`read_message` is async. Use a throwaway single-threaded `tokio` runtime or `std::io::Cursor` bridged via `tokio::io::AsyncRead`:

```rust
// fuzz_targets/read_message.rs
#![no_main]
use libfuzzer_sys::fuzz_target;
use std::io::Cursor;

fuzz_target!(|data: &[u8]| {
    let rt = tokio::runtime::Builder::new_current_thread()
        .build()
        .unwrap();
    rt.block_on(async {
        let mut cursor = tokio::io::BufReader::new(Cursor::new(data));
        // read_message reads 4-byte big-endian length prefix, then body.
        // Invariant: MAX_FRAME_LEN guard must fire before any unbounded allocation.
        let _ = nosh_proto::read_message(&mut cursor).await;
    });
});
```

Note: creating a tokio runtime on every fuzz iteration is expensive. An alternative is to use a `OnceCell<Runtime>` at module level. Verify which approach the fuzzer speed profile favours at implementation time. [ASSUMED]

### Pattern 3: Structured fuzz target with `#[derive(Arbitrary)]`

For `decode_datagram`, you can fuzz at two levels:
- **Raw bytes level:** Feed arbitrary `&[u8]` directly (catches tag/truncation/corruption).
- **Structured level:** Derive `Arbitrary` on the wire types and fuzz with structurally valid inputs to push coverage deeper into postcard decode paths.

For the raw-bytes path, the target is trivial (same as Pattern 1). For the structured path:

```rust
// fuzz_targets/decode_datagram.rs
#![no_main]
use arbitrary::Arbitrary;
use libfuzzer_sys::fuzz_target;

// Fuzz raw bytes — highest coverage for tag/truncation/corruption bugs.
fuzz_target!(|data: &[u8]| {
    let _ = nosh_proto::datagram::decode_datagram(data);
});
```

To add structured fuzzing (optional, higher coverage after raw-bytes baseline):

```rust
fuzz_target!(|data: &[u8]| {
    // Try as raw bytes first.
    let _ = nosh_proto::datagram::decode_datagram(data);
    // Also try with a valid tag + arbitrary body.
    if let Some((&tag_byte, body)) = data.split_first() {
        let tagged = [&[0x01u8], body].concat();
        let _ = nosh_proto::datagram::decode_datagram(&tagged);
    }
});
```

[ASSUMED: structured Arbitrary derive is beneficial here but raw-bytes is sufficient for the D-01 invariant. Verify at implementation time.]

### Pattern 4: OSC accumulation target

The OSC target feeds raw VT byte sequences into `TerminalState::advance()` and asserts the OSC caps hold:

```rust
// fuzz_targets/osc_accumulation.rs
#![no_main]
use libfuzzer_sys::fuzz_target;
use nosh_server::terminal::{TerminalState, OSC_52_MAX_BYTES, MAX_TITLE_BYTES};

fuzz_target!(|data: &[u8]| {
    let mut state = TerminalState::new(80, 24);
    state.advance(data);
    // Assert caps hold after arbitrary VT input.
    if let Some((_, clipboard_data)) = state.osc52_pending() {
        assert!(clipboard_data.len() <= OSC_52_MAX_BYTES,
            "OSC 52 exceeded cap: {} bytes", clipboard_data.len());
    }
    if let Some(title) = state.title() {
        assert!(title.len() <= MAX_TITLE_BYTES,
            "title exceeded cap: {} bytes", title.len());
    }
});
```

Note: `TerminalState::advance` calls `vte::Parser::advance` under the hood; this exercises `osc_dispatch`. [ASSUMED: the public API for `TerminalState` exposes `advance(&mut self, data: &[u8])` — verify the exact method signature in `crates/nosh-server/src/terminal.rs` before writing the target.]

### Pattern 5: QUIC-packet fuzzer via quinn-proto sans-IO `Endpoint::handle`

This is the key research finding. `quinn-proto 0.11.14` has a clean sans-IO API:

```rust
pub fn handle(
    &mut self,
    now: Instant,
    remote: SocketAddr,
    local_ip: Option<IpAddr>,
    ecn: Option<EcnCodepoint>,
    data: BytesMut,          // ← raw UDP packet bytes go here
    buf: &mut Vec<u8>,
) -> Option<DatagramEvent>
```

`DatagramEvent` has three variants: `ConnectionEvent` (packet routed to an existing connection), `NewConnection` (triggers a potential new connection), `Response` (endpoint sends a reply directly). The target feeds arbitrary bytes and asserts no panic.

Minimal in-process setup:

```rust
// fuzz_targets/quic_packet.rs
#![no_main]
use std::net::SocketAddr;
use std::sync::Arc;
use std::time::Instant;

use bytes::BytesMut;
use libfuzzer_sys::fuzz_target;
use quinn_proto::{Endpoint, EndpointConfig, ServerConfig};

// Build the endpoint once via lazy_static or std::sync::OnceLock.
// IMPORTANT: use_retry is NOT configured; quinn's default 3× anti-amplification applies.
fn make_server_endpoint() -> Endpoint {
    // EndpointConfig::default() requires the ring or aws-lc-rs feature (our workspace uses ring).
    let endpoint_cfg = Arc::new(EndpointConfig::default());
    // Build a minimal ServerConfig with a self-signed ephemeral cert (no real keys needed;
    // this fuzzer exercises OUR quinn config, not the TLS handshake internals).
    // Use the same build_server_config() helper from nosh-server, or build a minimal
    // rcgen self-signed cert + no-client-auth config for the fuzz target.
    //
    // VERIFY AT IMPLEMENTATION TIME: whether importing nosh-server's build_server_config
    // is feasible in the fuzz crate, or whether a stripped-down rcgen-based config
    // should be used instead (simpler, no authorized_keys file needed).
    let server_cfg = Arc::new(make_minimal_server_config());
    Endpoint::new(
        endpoint_cfg,
        Some(server_cfg),
        false,  // allow_mtud: false in fuzz context (deterministic)
        None,   // rng_seed: None (uses system entropy; fix to Some([0u8;32]) for reproducibility)
    )
}

fuzz_target!(|data: &[u8]| {
    use std::sync::OnceLock;
    static ENDPOINT: OnceLock<std::sync::Mutex<Endpoint>> = OnceLock::new();
    let endpoint = ENDPOINT.get_or_init(|| {
        std::sync::Mutex::new(make_server_endpoint())
    });

    let remote: SocketAddr = "127.0.0.1:12345".parse().unwrap();
    let now = Instant::now();
    let mut buf = Vec::new();
    let mut ep = endpoint.lock().unwrap();

    // Feed arbitrary bytes as a raw UDP packet. quinn-proto must not panic.
    let pkt = BytesMut::from(data);
    let _ = ep.handle(now, remote, None, None, pkt, &mut buf);
});
```

**Key design decisions for the QUIC fuzzer:**

1. Use `OnceLock<Mutex<Endpoint>>` so the endpoint is constructed once per fuzz process (construction is expensive; per-iteration construction collapses coverage). [ASSUMED: OnceLock-per-process works correctly with libFuzzer's in-process model]

2. The `rng_seed` parameter on `Endpoint::new` accepts `Option<[u8; 32]>`. Passing `Some([0u8; 32])` makes the endpoint's internal PRNG deterministic, improving reproducibility of crashes. [CITED: docs.rs/quinn-proto/0.11.14/quinn_proto/struct.Endpoint.html]

3. We are NOT testing quinn-proto internals — if the fuzzer finds a panic inside quinn-proto, that is a bug to report upstream. Our goal is to confirm our own config setup (`EndpointConfig::default()`, `ServerConfig` wiring, `migration(true)`) does not misuse the API in ways that cause our code to panic.

### Anti-Patterns to Avoid

- **Raw UDP socket to a real server process:** non-deterministic, slow, needs process management, crashes are hard to reproduce. Use the sans-IO `Endpoint::handle` path instead.
- **Fuzzing `encode_datagram`:** This is the encode path (trusted input); the decode path is the attack surface. Fuzz `decode_datagram` and `decode_epoch_ack`.
- **Forgetting `corpus/` seeds:** Without seed inputs, libFuzzer starts from random bytes and may take hours to penetrate even a 1-byte tag check. Seed each target with at least one valid encoding.
- **Creating a new `tokio::Runtime` per iteration in `read_message` fuzzer:** This is valid but slow. Consider `OnceCell<Runtime>` or using `std::io::Cursor` wrapped as a synchronous reader via a compatibility layer.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Coverage-guided fuzzing harness | Custom mutation engine | `cargo-fuzz` / libFuzzer | libFuzzer's edge-coverage feedback, minimisation, and corpus management are battle-tested; hand-rolling misses structured mutation |
| CVE scanning | Manual advisory lookup | `cargo-audit` | The RustSec advisory database is maintained by the security community; manual lookup will miss advisories |
| Structured arbitrary input generation | Manual bit-twiddling | `arbitrary` crate `#[derive(Arbitrary)]` | Arbitrary handles postcard varint ranges, `Vec` length limits, and enum discriminants correctly |
| Fuzz corpus seeding | Random byte files | Hand-craft valid serialized examples | Valid seeds give libFuzzer a starting point; random bytes struggle to pass even a 1-byte tag check |

## Pre-Auth Resource Audit (for D-04 doc)

### What `AuthLimits` currently caps

From `server.rs`:
- `max_concurrent: 64` — semaphore permits for simultaneous pre-auth connections
- `auth_timeout: Duration::from_secs(5)` — time before half-open connections are dropped

The semaphore is `try_acquire_owned()` — if all 64 permits are taken, `incoming.refuse()` is called immediately. This is the right pattern: refusal happens at the QUIC layer before any TLS state is allocated.

### What `quinn` allocates per half-open connection

[ASSUMED: quinn allocates a `Connection` struct per incoming datagram that passes initial packet validation (DCID routing, version check). The exact per-connection allocation size is not documented in the public API; it depends on quinn-proto internals. The audit doc should note this and reference the existing `preauth_flood_bounded` test as empirical evidence of bounded behaviour under load.]

Key observation from the flood test: 32 concurrent junk senders with a cap of 4 permits and a 1s timeout still allowed a legitimate client to connect. At the production default of 64 permits and 5s timeout, the bound is much more generous.

### Transport-level memory bounds

From `transport.rs`:
- `datagram_receive_buffer_size(Some(1 << 20))` — 1 MiB receive buffer per connection
- `datagram_send_buffer_size(1 << 20)` — 1 MiB send buffer per connection
- `max_idle_timeout(300s)` — finite, never `None` (prevents zombie connections)

At 64 half-open connections, worst-case QUIC buffer allocation is 64 × 2 MiB = 128 MiB for datagram buffers, plus quinn's internal per-connection structs. [ASSUMED: actual allocation will be lower because half-open connections do not reach the authenticated session stage where full datagram buffers are negotiated. Verify via memory profiling at implementation time.]

### Anti-amplification posture

QUIC RFC 9000 §8.1 mandates that servers send at most 3× the received bytes until the client address is validated. quinn-proto enforces this by default — the 3× limit applies until the TLS handshake completes and the client address is implicitly validated.

Our `ServerConfig` does NOT configure `ValidationTokenConfig` in any non-default way. The `migration(true)` call only affects already-authenticated connections, not the initial handshake. [ASSUMED: confirmed by API inspection — `quinn::ServerConfig::migration()` docs state it controls whether clients can migrate; it does not affect the initial address validation window.]

The audit doc should verify: does our `EndpointConfig::default()` configuration include retry token issuance? From inspection of `ValidationTokenConfig` docs: it configures NEW_TOKEN frames (sent after a validated path), not QUIC Retry packets. Retry token behaviour is a separate code path. [ASSUMED: confirm at implementation time whether `EndpointConfig::default()` issues Retry packets or relies on the 3× limit only. Check quinn-proto source: `Endpoint::handle` for `NewConnection` → whether `refuse()` / `retry()` / `ignore()` are called depends on config.]

## Common Pitfalls

### Pitfall 1: Workspace build breakage from fuzz crate

**What goes wrong:** `cargo build --workspace` or `cargo test --workspace` tries to compile `fuzz/fuzz_targets/*.rs`, which are `#[no_main]` binaries. This breaks the build with "entry symbol `main` not found" or similar.
**Why it happens:** If `fuzz/` is listed in `workspace.members`, cargo treats fuzz targets as regular binaries.
**How to avoid:** Add `exclude = ["fuzz"]` under `[workspace]` in the root `Cargo.toml`. The CI `cargo build --locked` and `cargo test --locked` commands will then never touch the fuzz crate.
**Warning signs:** CI failures with `no main function found` in fuzz_targets.

### Pitfall 2: Forgetting `--fuzzing-workspace=true` vs workspace exclusion

**What goes wrong:** `cargo fuzz init` by default assumes the fuzz crate joins the existing workspace (adds `fuzz` to `workspace.members`). But for this project, we want exclusion.
**How to avoid:** After `cargo fuzz init`, manually add `exclude = ["fuzz"]` to the root `Cargo.toml` and remove any auto-added `fuzz` from `members`. Alternatively, use `cargo fuzz init --fuzzing-workspace=true` to give the fuzz crate its own workspace from the start (cleaner). [ASSUMED: `--fuzzing-workspace=true` flag exists in cargo-fuzz 0.13.1 — verify with `cargo fuzz init --help`]

### Pitfall 3: Corpus directory not committed, then crash can't be reproduced

**What goes wrong:** Seed corpus files are gitignored (cargo-fuzz's default `.gitignore` excludes `corpus/` and `artifacts/`). Without seeds, another developer or a CI run cannot reproduce the fuzzer's starting state.
**How to avoid:** Override the default `.gitignore` in `fuzz/`: un-ignore `corpus/` but keep `artifacts/` ignored (crash artifacts are large and machine-specific). Commit the initial seed corpus per target.

### Pitfall 4: `read_message` fuzzer exhausts file descriptors

**What goes wrong:** Creating a `tokio::Runtime` on every fuzz iteration leaks thread pool resources if the runtime is not `block_on`-ed and dropped cleanly per iteration.
**How to avoid:** Use `OnceCell<Runtime>` at module level; call `runtime.block_on(async { ... })` per iteration. The runtime stays alive across iterations. OR: use `std::io::Cursor` + `tokio::io::BufReader` without a dedicated runtime by driving the future synchronously with `futures::executor::block_on`. [ASSUMED]

### Pitfall 5: QUIC fuzzer state accumulates between iterations (OnceLock approach)

**What goes wrong:** The `OnceLock<Mutex<Endpoint>>` approach reuses the endpoint across iterations. If a previous fuzz input caused the endpoint to reach a weird state (e.g., half-open connection registered in internal tables), subsequent iterations may behave differently.
**How to avoid:** This is acceptable for this fuzzer's goal (test OUR config, not state-machine coverage). If state accumulation becomes a problem, construct a fresh `Endpoint` per iteration (slower) or call `Endpoint::new()` with `rng_seed = Some(...)` for determinism. [ASSUMED]

### Pitfall 6: `cargo audit` install time in CI

**What goes wrong:** `cargo install cargo-audit` on every CI run takes 2-5 minutes and flakes on network issues.
**How to avoid:** Use the `actions-rust-lang/audit@v1` GitHub Action (maintained, installs a prebuilt binary). It requires no `cargo install` step and handles the advisory DB fetch automatically.

## Code Examples

### Seed corpus construction for `codec_decode`

Create `fuzz/corpus/codec_decode/` with a small set of valid postcard-encoded `Message` bodies (WITHOUT the 4-byte length prefix — `codec::decode` takes the body only):

```rust
// One-time script to generate seed files:
// cargo run --example gen_corpus (or inline in a test)
use nosh_proto::{Message, codec};

fn main() {
    let msgs = vec![
        Message::SessionClose { exit_code: 0, reason: "ok".into() },
        Message::Resize { cols: 80, rows: 24 },
        Message::PtyData { data: vec![0x03] },
    ];
    for (i, msg) in msgs.iter().enumerate() {
        let frame = codec::encode(msg).unwrap();
        let body = &frame[4..]; // strip length prefix
        std::fs::write(format!("fuzz/corpus/codec_decode/{i:04}"), body).unwrap();
    }
}
```

## Open Questions (RESOLVED)

> Resolution summary (all three are settled for planning — none blocks the plan):
> - **Q1 (Retry default):** RESOLVED — deferred to implementation: plan 999.1-05 Task 1 reads `quinn-proto/src/endpoint.rs` `handle()` for `self.retry()`/`self.refuse()` and records the finding (with a source citation) in the security doc. The 3× anti-amplification limit holds regardless; Retry is an optional stronger guarantee to document.
> - **Q2 (read_message runtime):** RESOLVED — use `OnceLock<Runtime>` (per PATTERNS.md read_message shape); switch to per-iteration only if it ever matters.
> - **Q3 (QUIC fuzzer config):** RESOLVED — use an independent minimal rcgen self-signed no-client-auth `ServerConfig` (plan 999.1-04 action), NOT the `build_server_config()` key-file chain.

1. **Does `EndpointConfig::default()` issue QUIC Retry packets?**
   - What we know: `ValidationTokenConfig` (the documented config struct) manages NEW_TOKEN frames, not Retry.
   - What's unclear: Whether quinn-proto's default `Endpoint` issues Retry packets pre-handshake.
   - Recommendation: At implementation time, read `quinn-proto/src/endpoint.rs` `handle()` method — look for calls to `self.retry()` or `self.refuse()` in the `NewConnection` arm. If Retry is NOT issued by default, document this in the security doc as "3× limit is the only anti-amplification mechanism; consider enabling Retry for stronger guarantees."

2. **`read_message` fuzz target: `tokio::Runtime` per-iteration vs `OnceCell`?**
   - What we know: Per-iteration runtime construction is valid but slow.
   - What's unclear: Which approach gives better fuzzer throughput on this target.
   - Recommendation: Start with `OnceCell<Runtime>` (faster); switch to per-iteration if corpus sharing between concurrent fuzzer processes becomes an issue.

3. **Should the QUIC fuzzer use `nosh-server::build_server_config()` or an independent minimal config?**
   - What we know: `build_server_config()` requires `host_key_path` and `authorized_keys_path` on disk — manageable in a fuzz target via `tempfile`, but adds complexity.
   - What's unclear: Whether the extra realism (testing our actual config chain) is worth the complexity.
   - Recommendation: Use an independent minimal rcgen self-signed cert + no-client-auth `ServerConfig` for the QUIC fuzzer. The goal is to test whether our `EndpointConfig` + `migration(true)` setup panics on hostile input, not to fuzz the auth logic (which is separately tested by `mutual_auth_inprocess_happy_path`).

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malformed postcard → OOM | Denial of Service | MAX_FRAME_LEN (16 MiB), MAX_RUNS (4096) — fuzz to confirm |
| Length-prefix abuse (huge `len`) | Denial of Service | `if len > MAX_FRAME_LEN { return Err }` before `vec![0u8; len]` |
| Tag byte manipulation (0x01/0x02) | Tampering | Tag check in `decode_datagram` / `decode_epoch_ack` before deserialization |
| QUIC amplification (spoofed IP) | Denial of Service | quinn 3× limit pre-handshake; `incoming.refuse()` at permit cap |
| Half-open connection flood | Denial of Service | AuthLimits semaphore; 5s auth timeout; existing `preauth_flood_bounded` test |
| OSC 52 large-payload OOM | Denial of Service | `OSC_52_MAX_BYTES` (65 536) truncation in `osc_dispatch` before store |
| OSC 0/2 large-title OOM | Denial of Service | `MAX_TITLE_BYTES` (1 024) discard in `osc_dispatch` |
| Transitive dep CVE | Tampering/Info Disclosure | cargo-audit against RustSec DB |
