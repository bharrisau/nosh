# Phase 999.1: Code Review Report

**Reviewed:** 2026-06-07
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Six cargo-fuzz harnesses for the nosh-proto decoders and the QUIC packet path, plus CI audit and deny.toml configuration. The harnesses for `codec_decode`, `decode_datagram`, `decode_epoch_ack`, and `read_message` correctly exercise the target functions over raw fuzz bytes without sanitisation or structural over-constraint. The cap assertions in `osc_accumulation` are non-tautological and the `deny.toml` licence list is conservative and well-annotated.

The principal concern — and the reason the overnight campaign gives false confidence — is that vte's unbounded OSC accumulation buffer is a production-code DoS path that the `osc_accumulation` harness structurally cannot reach at libfuzzer's default input sizes. The harness tests the `osc_dispatch` cap correctly, but that cap is applied _after_ vte has already allocated into its internal `Vec<u8>` buffer, which is the real attack surface.

Two secondary issues: the `quic_packet` harness leaks quinn-proto `Incoming` state on every iteration that produces a valid-looking QUIC Initial packet (quinn-proto explicitly warns about this in its Drop impl), and the `read_message` harness carries a false comment about when the 16 MiB allocation guard fires.

## Critical Issues

### CR-01: vte "std" enables unbounded OSC buffer before `osc_dispatch` — harness cannot detect it

**File:** `fuzz/fuzz_targets/osc_accumulation.rs:8`
**Also affects:** `crates/nosh-server/src/terminal.rs:41`, `crates/nosh-server/Cargo.toml`

**Issue:** With the `std` feature active (the vte 0.15 default, explicitly used by `nosh-server`), vte's internal `osc_raw` field is a `Vec<u8>` that grows without bound as OSC bytes are fed byte-by-byte through `advance()`. The `is_full()` guard on `action_osc_put` (vte lib.rs:547) is compiled out under `#[cfg(not(feature = "std"))]`. The `osc_dispatch` caps applied in `terminal.rs` (`OSC_52_MAX_BYTES = 65_536`, `MAX_TITLE_BYTES = 1_024`) run _after_ vte has finished accumulating the full sequence into `osc_raw`. A server process emitting `OSC 52 ; c ; <1 GB base64> BEL` will grow `osc_raw` to 1 GB before `osc_dispatch` is called, causing server OOM.

The `osc_accumulation` harness cannot expose this because libfuzzer's default `max_len` is 4 096 bytes — the harness inputs are too short to stress the vte accumulation path. The overnight "ZERO crashes" result is therefore false confidence on the actual production DoS vector. The invariant comment on line 7 ("no unbounded alloc") is incorrect for inputs that arrive from real PTY output.

Verified by reading `vte-0.15.0/src/lib.rs` lines 544–551:
```rust
fn action_osc_put(&mut self, byte: u8) {
    #[cfg(not(feature = "std"))]
    {
        if self.osc_raw.is_full() {   // guard ONLY active without "std"
            return;
        }
    }
    self.osc_raw.push(byte);  // Vec<u8>, no cap with "std"
}
```

**Fix options (choose one):**

Option A — Revert to `default-features = false` for vte (uses `ArrayVec<u8, 1024>` for `osc_raw`), accepting the 1 024 byte OSC payload limit. Phase 16 chose to re-enable "std" to support 64 KB OSC 52 clipboard writes. If that use case is retained, Option B is required.

Option B — Add a streaming byte-count guard in `terminal.rs::advance()` that aborts OSC accumulation above a threshold, by wrapping the input slice before passing to the parser. Concretely, feed the parser in chunks and skip bytes past a running OSC-byte counter that resets on each sequence terminator. This is more invasive.

Option C (minimum viable) — Cap the input to the vte parser in `advance()` when the parser is in OSC state. The simplest form: do not call `parser.advance(self, bytes)` when `bytes.len()` exceeds a threshold in a single call. This is incomplete (multi-call sequences bypass it) but bounds single-call exposure.

The harness should also be updated to run with a much larger `max_len` (e.g. `-max_len=131072`) to expose this path, and a seed file `fuzz/corpus/osc_accumulation/large_osc52` containing `\x1b]52;c;` followed by 128 KiB of `A` and `\x07` should be added.

## Warnings

### WR-01: `quic_packet` harness leaks `Incoming` state — quinn-proto explicitly warns about OOM

**File:** `fuzz/fuzz_targets/quic_packet.rs:131`

**Issue:** When `ep.handle()` returns `Some(DatagramEvent::NewConnection(incoming))`, the harness discards the return value via `let _ = ep.handle(...)`, causing `Incoming` to be dropped without passing it to `ep.ignore()`, `ep.accept()`, or `ep.refuse()`. Quinn-proto's `Drop` impl for `IncomingImproperDropWarner` emits:

> "may cause memory leak and eventual inability to accept new connections"

The endpoint's `incoming_buffers: Slab<IncomingBuffer>` and its connection ID index entry are not freed when `Incoming` is dropped. Over millions of fuzz iterations, any input that produces a syntactically plausible QUIC Initial packet (correct version field, valid-length CID, non-empty payload) will accumulate one `Slab` entry. The `incoming_buffer_size_total` default (100 MiB) bounds byte accumulation but not the number of orphaned `Slab` entries.

The harness comment at line 108 labels this "state accumulation is intentional (Pitfall 5)" and says the goal is "config-misuse detection, not state-machine coverage." This reasoning is partially correct but does not eliminate the risk: if the fuzz corpus evolves to produce many valid-looking Initial packets (which the coverage-guided fuzzer will do), the endpoint's connection table grows towards the fuzzer process OOM limit. A hidden long-campaign OOM would manifest as an unexplained fuzzer exit, not a crash in the target.

Verified in `quinn-proto-0.11.14/src/endpoint.rs:1224–1229`.

**Fix:**
```rust
use quinn_proto::DatagramEvent;

let pkt = BytesMut::from(data);
match ep.handle(now, remote, None, None, pkt, &mut buf) {
    Some(DatagramEvent::NewConnection(incoming)) => {
        // Must call ignore() to free the Slab entry and CID index.
        ep.ignore(incoming);
    }
    Some(DatagramEvent::Response(_)) | None => {}
    // ConnectionEvent is unreachable (no open connections), but handle exhaustively.
    Some(DatagramEvent::ConnectionEvent { .. }) => {}
}
buf.clear();
```

`ep.ignore()` is defined at `quinn-proto-0.11.14/src/endpoint.rs:774–777` and removes both the `Slab` entry and the CID-to-incoming index entry.

### WR-02: `read_message` harness comment misrepresents the allocation guard — 16 MiB can be allocated per iteration

**File:** `fuzz/fuzz_targets/read_message.rs:18–19`

**Issue:** The comment states: _"Invariant: MAX_FRAME_LEN guard fires BEFORE vec![0u8; len] allocation."_ This is false for the boundary value. `codec::read_message` (codec.rs:71) checks `if len > MAX_FRAME_LEN { return Err }` — a strict greater-than. When the first four fuzz bytes encode exactly `MAX_FRAME_LEN` (0x01_00_00_00 in big-endian), `len == 16_777_216` passes the guard and the allocation `vec![0u8; 16_777_216]` on line 74 proceeds before `read_exact` fails with `UnexpectedEof`. A four-byte input `[0x01, 0x00, 0x00, 0x00]` — which libfuzzer will generate quickly — causes a 16 MiB allocation per iteration, substantially reducing fuzzer throughput.

The misleading comment also creates false assurance about the production guard: the check should arguably be `>= MAX_FRAME_LEN` (to reject exactly-at-limit frames) or the comment should be corrected to reflect the actual semantics.

**Fix (two parts):**

Part 1 — Correct the guard in `crates/nosh-proto/src/codec.rs:71` to `>=` if the intent is to reject frames at or above the limit:
```rust
if len >= MAX_FRAME_LEN {
    return Err(ProtoError::FrameTooLarge(len));
}
```

Part 2 — Or, if `== MAX_FRAME_LEN` frames are intentionally valid, correct the harness comment to:
```rust
// Note: the guard rejects len > MAX_FRAME_LEN (strict). A 4-byte input encoding
// exactly MAX_FRAME_LEN will allocate a 16 MiB vec before read_exact fails.
// This slows throughput but is structurally correct.
```

## Info

### IN-01: `deny.toml` [advisories] does not explicitly set `vulnerability`

**File:** `deny.toml:5–8`

**Issue:** The `[advisories]` section sets `unmaintained = "workspace"` and `unsound = "all"` but omits `vulnerability`. Cargo-deny >= 0.14 defaults `vulnerability` to `"deny"`, but this is not explicit. Anyone reading the config file cannot tell at a glance whether CVE-level advisories block CI or are merely warned about. There is also no `[advisories]` db-path configured, so `cargo deny check` fetches the advisory database on every run (network dependency, flaky in airgapped environments).

**Fix:**
```toml
[advisories]
vulnerability  = "deny"
unmaintained   = "workspace"
unsound        = "all"
```

### IN-02: Fuzz workspace `Cargo.lock` packages not covered by CI `cargo-audit` job

**File:** `.github/workflows/ci.yml:54–62`

**Issue:** `actions-rust-lang/audit@v1` runs from the repository root and audits the root `Cargo.lock`. The fuzz crate is a separate workspace (`fuzz/Cargo.toml:[workspace]`) with its own `fuzz/Cargo.lock`. Packages that exist only in the fuzz lock file — `libfuzzer-sys`, `arbitrary`, `derive_arbitrary`, `fastbloom`, `jobserver`, `siphasher` — are not audited by the CI job. Of these, `libfuzzer-sys` links C code (LLVM libFuzzer) and `jobserver` is a build tool; both could carry RUSTSEC advisories that go undetected.

The core project deps (quinn, rcgen, rustls, etc.) appear in both lock files, so their advisories are covered.

**Fix:** Add a second audit step in CI, or use `cargo-deny` (which supports multiple workspace roots) as an alternative. Minimal fix:
```yaml
- name: Audit fuzz dependencies
  run: cargo audit --manifest-path fuzz/Cargo.toml
```
Note: `cargo audit` on the fuzz manifest requires `cargo-audit` installed on the runner; the `actions-rust-lang/audit` action handles installation, so a second step with that action and `working-directory: fuzz` is the cleanest approach.
