# Phase 999.4: Code Review Report

**Reviewed:** 2026-06-05

## Summary

Three changes were introduced this phase: (1) a new `InputAction::PredictEnter` variant that predicts the cursor line-advance on Enter/newline instead of calling `EpochReset`; (2) per-call decision-trace instrumentation in `on_input`; (3) a BulkSuppressed refinement that preserves existing predictions via `become_tentative` rather than always calling `reset`.

None of the changes introduce security vulnerabilities or data-loss risks. The noecho suppression invariant holds for PredictEnter — `become_tentative` is called, subsequent char predictions are tentative and hidden, and the line-advance cursor position reveals only that Enter was pressed (not character content), which is consistent with terminal behaviour regardless of echo state. The CR-01 property for the EpochReset path (Tab/ESC) is correctly maintained by `reset_with_cursor` + `needs_epoch_start_sync`.

Two warnings and one info item were found: a `needs_epoch_start_sync` misapplication in the BulkSuppressed/become_tentative path that can transiently corrupt `epoch_start_col` mid-epoch, and four early-return paths in `on_input` that silently skip the D-03 trace event. The `cursor_motion_pending = false` write at PredictEnter line 443 (immediately overwritten at line 457) is a dead write recorded as an info item.

## Warnings

### WR-01: BulkSuppressed/become_tentative sets `needs_epoch_start_sync` incorrectly mid-epoch

**File:** `crates/nosh-client/src/predictor.rs:470-473`

**Issue:** When `BulkSuppressed` fires with `pending.len() > 0`, the new code calls `become_tentative()` and sets `needs_epoch_start_sync = true`. `needs_epoch_start_sync` is the signal that the next `sync_cursor_from_confirmed` call should overwrite `epoch_start_col` with the confirmed cursor column. That signal is correct after a full epoch boundary (Enter, Ctrl-C, Tab) where a new prompt line has begun. It is NOT correct mid-epoch: the BulkSuppressed burst happened during active typing at the current prompt, not at a prompt boundary. Setting the flag here causes the very next confirming datagram to update `epoch_start_col` to wherever the confirmed cursor lands after the burst — which is some mid-line column, not the actual prompt start.

Concretely: user types "abc" at prompt col 2 → `epoch_start_col = 2`, `predicted_cursor.col = 5`. A key-repeat burst with an escape byte fires → BulkSuppressed, pending > 0 → `become_tentative()` + `needs_epoch_start_sync = true`. Server confirms the "abc" chars → `sync_cursor_from_confirmed` fires with confirmed col = 5 → `epoch_start_col` is now incorrectly set to 5. The user can no longer backspace past col 5, even though the real prompt boundary is col 2. This is the BUG-E symptom (cursor clamped at wrong floor) reintroduced for the BulkSuppressed mid-epoch path.

The self-correction window is short: it lasts until the next PredictEnter/EpochReset (the user's next Enter or Ctrl-C), which resets `needs_epoch_start_sync` again and sets up a proper epoch-boundary sync. But in the interim, backspace and PredictCursorLeft are clamped at the wrong floor.

**Fix:** Remove `self.needs_epoch_start_sync = true;` from the BulkSuppressed/become_tentative branch. A mid-epoch become_tentative is not an epoch boundary; the existing `epoch_start_col` (set at the true prompt boundary) should be preserved:

```rust
InputAction::BulkSuppressed => {
    if self.pending.is_empty() {
        self.reset();
    } else {
        self.become_tentative();
        // Do NOT set needs_epoch_start_sync here: BulkSuppressed fires mid-epoch
        // (during typing at the current prompt), not at a prompt boundary. Overwriting
        // epoch_start_col with the mid-burst confirmed cursor would misplace the
        // backspace/cursor-left clamp floor (BUG-E) until the next EpochReset.
        // The existing epoch_start_col (set at the true prompt start) is still valid.
    }
}
```

### WR-02: D-03 trace event skipped on four early-return paths in `on_input`

**File:** `crates/nosh-client/src/predictor.rs:340, 347, 494, 505`

**Issue:** The D-03 instrumentation places a single `tracing::debug!` call at the end of `on_input` (after the `match` block). Four paths inside the `match` return early via `return`, bypassing the trace event entirely:

1. `PredictChar` during `in_bracketed_paste` (line 340) — `return` skips the event.
2. `PredictChar` at right-edge wide-char (line 347) — `return` skips the event.
3. `PredictBatch` during `in_bracketed_paste` (line 494) — `return` skips the event.
4. `PredictBatch` at right-edge wide-char (line 505) — `return` skips the event.

The D-03 design intent is "one debug event per `on_input` call." These four paths are invisible to the trace, defeating the diagnostic value of the instrumentation for exactly the suppression paths that are hardest to debug in production (bracketed paste and wide-char right-edge). They were pre-existing early returns, but D-03 was supposed to cover all paths.

**Fix:** Move the `tracing::debug!` call to a helper or restructure to avoid early returns, OR add a `batch_len` / `action` capture before the match and emit the trace at the return sites:

```rust
pub fn on_input(&mut self, bytes: &[u8], screen: &ClientScreen) {
    let pending_before = self.pending.len();
    let action = classify_input(bytes);
    let action_kind = action_kind_tag(&action);
    // Macro to emit the trace at any exit point.
    macro_rules! trace_exit {
        () => {
            tracing::debug!(
                target: "nosh::predict",
                event = "on_input",
                batch_len = bytes.len(),
                action = action_kind,
                pending_before,
                pending_after = self.pending.len(),
                predictions_dropped = pending_before.saturating_sub(self.pending.len()),
                pred_row = self.predicted_cursor.row,
                pred_col = self.predicted_cursor.col,
            );
        };
    }
    match action {
        InputAction::PredictChar { ch, col_width } => {
            if self.in_bracketed_paste {
                trace_exit!();
                return;
            }
            // ...
            if col.saturating_add(col_width) > self.term_cols {
                self.become_tentative();
                trace_exit!();
                return;
            }
            // ... rest of arm ...
        }
        // ... other arms ...
    }
    trace_exit!();
}
```

Alternatively, refactor the early-return guards to use a flag rather than early return, keeping the single trace call at the end.

### IN-01: Dead write to `cursor_motion_pending` in PredictEnter arm

**File:** `crates/nosh-client/src/predictor.rs:443`

**Issue:** The PredictEnter arm writes `self.cursor_motion_pending = false` at line 443, then unconditionally writes `self.cursor_motion_pending = true` at line 457 with no conditional branch, loop, or function call between them. The `false` write has no observable effect: no code path reads `cursor_motion_pending` between these two assignments within `on_input` (it is only read by external callers of `sync_cursor_from_confirmed` and `predicted_cursor`, neither of which is called within `on_input`). The intermediate state is invisible.

This pattern suggests the author may have intended the `false` write to allow a hypothetical `sync_cursor_from_confirmed` call mid-arm (a guard that doesn't exist), or it is a vestige of an earlier draft. As written, it misleads future readers into thinking the two assignments serve distinct purposes.

**Fix:** Remove the dead write at line 443:

```rust
InputAction::PredictEnter => {
    self.pending.clear();
    self.become_tentative();
    // cursor_motion_pending = false removed (dead write — overwritten unconditionally at line 457)
    self.needs_epoch_start_sync = true;
    self.epoch_start_col = 0;
    let row = self.predicted_cursor.row;
    if row < self.term_rows.saturating_sub(1) {
        self.predicted_cursor = CursorPos { row: row + 1, col: 0 };
    } else {
        self.predicted_cursor = CursorPos { row, col: 0 };
    }
    self.cursor_motion_pending = true;
}
```
