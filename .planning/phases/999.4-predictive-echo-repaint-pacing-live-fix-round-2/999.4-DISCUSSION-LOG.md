## Repaint pacing

Operator asked whether the cause is that the server doesn't absorb vim's output until it sends a
packet, and whether the 16 ms is decoupled so vim can dump all lines and we pack as much as
possible per MTU. Investigation confirmed: the terminal model IS decoupled (fed on
`out_rx.recv()` → `push_output_and_parse`, `server.rs:612`); the only limiter is one MTU datagram
per 16 ms tick (`server.rs:676-712`), with overflow deferred. No QUIC flow-control ceiling.

→ **D-01: burst multiple MTU datagrams per tick, congestion-bounded.** (Operator's intuition was
correct.) Research needed on quinn datagram-under-congestion to pick the per-tick budget.
Reliable-stream fallback explicitly NOT taken (deferred).

## read -s newline

Operator clarified: on standard SSH the first Enter (running `read -s SECRET; echo done`) drops
the caret to the next line; secret chars hidden; final Enter prints done + new prompt. nosh leaves
the caret on the command line. Operator: "handle the first enter without the SECRET, then only
enter secret mode after."

→ **D-02: positively predict the command-submitting Enter's line-advance at an echoing prompt;**
existing noecho machinery hides the following secret chars. Mosh-style newline prediction.

## Fast-typing glitch

Operator: "give me the tools to instrument it. Very easy to reproduce — holding a key or mashing
the keyboard causes glitches where letters look like they disappear." Slow typing is fine.

→ **D-03: instrument-first.** Add a predictor decision-trace (classification, pending count
before/after, reset/cull drops, predicted vs confirmed cursor); operator reproduces; hypothesis
fix = a mid-burst reset() clearing already-shown pending predictions, with a regression test.
