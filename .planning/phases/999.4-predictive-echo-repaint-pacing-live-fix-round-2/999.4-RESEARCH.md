## Summary

Three focused questions required research; all three are answered with HIGH confidence from
authoritative source (quinn-proto source at tag quinn-0.11.8, Mosh terminaloverlay.cc HEAD, live
codebase read).

**D-01 (burst budget):** quinn's `send_datagram` is backed by an application-level queue
(1 MiB, configured in transport.rs). The queue is drained by the protocol layer subject to the
congestion controller and pacer — datagrams are congestion-controlled per RFC 9221. The key
API is `conn.datagram_send_buffer_space()`, which returns bytes free in the application queue
before older datagrams would be dropped. Using this as the per-tick send gate is the correct,
congestion-transparent approach: call `send_datagram` in a loop while space remains and a diff
run is available, without requiring direct access to the congestion window.

**D-02 (Enter newline prediction):** Mosh's `newline_carriage_return()` does two things: set
cursor col to 0, and if the cursor is already on the last row, expire all cells on that row as
blank predictions (scroll placeholder) rather than predicting row+1. Our implementation should
mirror this exactly but using our flat `VecDeque<PendingPrediction>` model: when Enter fires at
`EpochReset`, predict cursor → `(row+1, 0)` if row < last row, or `(row, 0)` with a blank-row
prediction if on the last row. The existing tentative/noecho machinery already suppresses this
prediction in noecho epochs — the cursor prediction becomes tentative and hidden.

**D-03 (fast-typing disappearing letters):** The most likely cause is confirmed: a mid-burst
`EpochReset` or `BulkSuppressed` classification (classifying a key-repeat batch containing a
CR or control char) calls `reset()`, clearing all `pending`. Instrumentation needs to capture
classification + pending-before/after on every `on_input` call to prove exactly when and why.
Mosh does not have an equivalent "pending drops" problem because it uses `cull()` (which is
called against a confirmed framebuffer state) rather than resetting on every keystroke; our
design is structurally different but the fix is the same: the burst-reset path should not clear
already-visible predictions if the burst is entirely printable.

**Primary recommendation:** Implement D-01 by looping `send_datagram` while
`conn.datagram_send_buffer_space() >= cap` within the diff tick arm. Implement D-02 by splitting
`EpochReset` handling for Enter vs other reset triggers. Implement D-03 instrumentation in
`on_input` with a single `tracing::debug!` per call under `target: "nosh::predict"`.

## Q1: quinn Datagram Burst Semantics (D-01)

### quinn version in this repo

`quinn` 0.11.9 (from Cargo.lock checksum
`b9e20a958963c291dc322d98411f541009df2ced7b5a4f2bd52337638cfccf20`). Research verified against
source tag `quinn-0.11.8` (no 0.11.9 tag exists; patch-level changes are unlikely to affect
this API surface). [VERIFIED: github.com/quinn-rs/quinn source]

### Two-layer queue model

quinn separates the datagram pipeline into two layers:

**Layer 1 — Application queue** (`datagrams.outgoing: VecDeque<Datagram>`, bounded by
`datagram_send_buffer_size`): this is where `conn.send_datagram(bytes)` enqueues. The 1 MiB
`datagram_send_buffer_size` in `transport.rs:9` is this layer's bound. `send_datagram` enqueues
with `drop = true`, meaning when the 1 MiB buffer is full it pops the oldest entry rather than
returning an error — no `Blocked` variant in our path. [VERIFIED: quinn-rs/quinn datagrams.rs]

**Layer 2 — Protocol transmit loop** (`poll_transmit`): the QUIC protocol layer dequeues from
Layer 1 and packs datagrams into UDP packets, subject to: (a) the congestion window
(`path.congestion.window()`), (b) the pacer, and (c) anti-amplification limits. Multiple
application datagrams can be packed into one UDP datagram via GSO. [VERIFIED:
quinn-rs/quinn connection/mod.rs]

### `send_datagram` vs `send_datagram_wait` — which to use

`send_datagram(bytes) -> Result<(), SendDatagramError>`:
- Enqueues immediately; drops oldest pending datagram if Layer 1 queue is full.
- Returns `Err` only for: `TooLarge`, `UnsupportedByPeer`, `Disabled`, `ConnectionLost`.
- Does NOT block or return `Blocked` in this variant (drop=true path). [VERIFIED: quinn docs.rs 0.11.9]

`send_datagram_wait(bytes) -> SendDatagram<'_>` (Future):
- Waits for Layer 1 queue space before enqueuing; preserves FIFO order.
- Effectively provides back-pressure: new datagrams do not displace old ones.
- **Do not use for the burst loop** — it would serialize sends across tick boundaries and
  reintroduce the single-datagram-per-tick bottleneck.

### `datagram_send_buffer_space()` — the correct budget API

`conn.datagram_send_buffer_space() -> usize`:
- Returns: `datagram_send_buffer_size.saturating_sub(datagrams.outgoing_total)`.
- Semantics: when the return value is >= N bytes, calling `send_datagram` with an N-byte
  datagram is guaranteed not to drop any older queued datagram.
- Does NOT reflect the congestion window directly. The congestion window governs Layer 2
  (when the protocol drains Layer 1), not Layer 1 enqueue.
- Implication: if you fill Layer 1 faster than Layer 2 can drain it under congestion, oldest
  datagrams are dropped — which is exactly the correct behaviour for latest-state-wins
  datagrams. The client always reconciles from the latest epoch it receives.
  [VERIFIED: quinn-rs/quinn datagrams.rs `send_buffer_space` method]

### RFC 9221 congestion control interaction

RFC 9221 §5: "DATAGRAM frames are subject to the QUIC connection's congestion controller."
The sender MUST delay or drop the frame when the controller cannot allow it. Quinn implements
this in `poll_transmit`: datagrams are only emitted when `path.in_flight.bytes +
bytes_to_send < path.congestion.window()` and pacing allows. [CITED: RFC 9221 §5;
VERIFIED: quinn-rs/quinn connection/mod.rs poll_transmit lines 596-619]

The practical consequence: under a slow or congested path, Layer 2 drains slowly, Layer 1
fills. Once Layer 1 fills (1 MiB), subsequent `send_datagram` calls drop the oldest enqueued
datum — not an error. The client receives only the latest datagrams that fit the congestion
window, which is the desired behaviour.

### Recommended per-tick burst strategy

**Approach:** at each 16 ms diff tick, loop calling `build_state_diff` (consuming the deferred
queue) and `send_datagram` until there are no more deferred runs to send OR the Layer 1 queue is
nearly full.

```rust
// In the diff_interval.tick() arm — replace the current single-datagram call:
let cap = match conn.max_datagram_size() {
    Some(c) if c >= MIN_CAP => c,
    _ => continue,
};

loop {
    // Budget gate: stop if Layer 1 queue has less than one datagram's worth of free space.
    // This prevents the burst from displacing datagrams enqueued in a previous tick
    // that have not yet been drained by the protocol layer under congestion.
    let space = conn.datagram_send_buffer_space();
    if space < cap {
        break;
    }

    let deferred = std::mem::take(&mut pending_deferred);
    let nothing_to_send = deferred.is_empty();

    match build_state_diff(
        &slot,
        &mut current_epoch,
        last_acked_epoch,
        &last_acked_snapshot,
        &last_sent_snapshot,
        deferred,
        cap,
    ) {
        None => {
            // Nothing to send (grid unchanged + client caught up), OR encoding failed.
            break;
        }
        Some(result) => {
            epoch_snapshots.push_back((result.epoch, result.sent_cells.clone()));
            if epoch_snapshots.len() > EPOCH_SNAPSHOT_CAP {
                epoch_snapshots.pop_front();
            }
            last_sent_snapshot = result.sent_cells;
            pending_deferred = result.deferred;

            if let Err(e) = conn.send_datagram(result.payload) {
                use quinn::SendDatagramError::*;
                match e {
                    TooLarge => {} // encode_datagram guarantees this is unreachable
                    UnsupportedByPeer | Disabled | ConnectionLost(_) => {
                        break SessionEnd::TransportLost;
                    }
                }
            }

            // Stop when no more runs are deferred (full diff fit in this batch).
            if pending_deferred.is_empty() {
                break;
            }
        }
    }
}
```

**Key property of this approach:**
- All deferred runs are sent in one tick when the path allows it (space available, congestion
  window permits drain).
- Under a slow path, older datagrams in Layer 1 may be dropped to make room, but that is
  correct for latest-state-wins semantics.
- The `space < cap` guard prevents the loop from queueing N+1 datagrams when only N fit
  without displacement.

**Alternative: datagram count cap** (e.g. max 8 per tick):
- Simpler to reason about, but requires a calibrated constant.
- Fails the goal when a 1080-cell vim screen needs 50 datagrams: the repaint still dribbles.
- Not recommended unless `datagram_send_buffer_space` proves unreliable in practice.

**Do NOT:** read the congestion window directly (`conn.rtt()` or internal state) — it is not
exposed on `quinn::Connection` in 0.11.9. The `datagram_send_buffer_space` proxy is the
only stable API for this. [ASSUMED — no congestion window accessor confirmed on the public API
in 0.11.9; verify at implementation time that `datagram_send_buffer_space` is on
`quinn::Connection` not only `quinn_proto::connection::Datagrams`]

**Verify at implementation time:**
- `conn.datagram_send_buffer_space()` must be called on the `quinn::Connection` public type
  (not the internal `quinn_proto` type). Confirm the method is present on
  `quinn::Connection` in 0.11.9 by checking `docs.rs/quinn/0.11.9/quinn/struct.Connection.html`
  before wiring the loop. The docs.rs summary confirmed it exists [VERIFIED: docs.rs 0.11.9
  WebFetch], but the exact method name should be checked against the live source.

### `build_state_diff` loop termination condition

`build_state_diff` returns `None` when the grid is unchanged and the client is caught up
(no deferred runs and `cells == last_acked_snapshot`). This naturally terminates the burst loop
when the full diff has been sent — no extra state needed. When `result.deferred.is_empty()`,
the full diff fit in this iteration; break.

## Q2: Mosh Enter / Newline Line-Advance Prediction (D-02)

### What Mosh does in `newline_carriage_return`

Source: `mobile-shell/mosh src/frontend/terminaloverlay.cc:830-862` [VERIFIED: GitHub API read]

```cpp
void PredictionEngine::newline_carriage_return( const Framebuffer& fb )
{
  uint64_t now = timestamp();
  init_cursor( fb );
  cursor().col = 0;                              // Always: move to column 0.
  if ( cursor().row == fb.ds.get_height() - 1 ) {
    // On last row: predict that the current row's cells will become blank
    // (the row scrolls off). Do NOT predict row+1 — that's the scroll case.
    // Instead, expire all cells on the current row as blank.
    // (Actual scroll prediction is commented out: "Don't try to predict
    // scroll until we have versioned cell predictions".)
    ConditionalOverlayRow& the_row = get_or_make_row( cursor().row, fb.ds.get_width() );
    for ( auto& j : the_row.overlay_cells ) {
      j.active = true;
      j.tentative_until_epoch = prediction_epoch;
      j.expire( local_frame_sent + 1, now );
      j.replacement.clear();   // blank cell
    }
    // cursor().row stays the same — row+1 is not predicted.
  } else {
    cursor().row++;             // Not at last row: advance row.
  }
}
```

This is called from the `CR` (0x0d) Execute action handler:
```cpp
} else if ( type_act == typeid( Parser::Execute ) ) {
  if ( act.char_present && ( act.ch == 0x0d ) /* CR */ ) {
    become_tentative();
    newline_carriage_return( fb );
  }
```

Also called when a character wraps past the right edge of the terminal:
```cpp
} else {
  become_tentative();
  newline_carriage_return( fb );  // wrap-around case
}
```

### What this means for our `predictor.rs` EpochReset handler

Currently, `EpochReset` for Enter calls only `reset_with_cursor(screen.confirmed_cursor())`,
which snaps the predicted cursor to the confirmed cursor position and clears pending
predictions. This is correct for Tab/ESC/other epoch-resets — but for Enter at a
non-secret prompt, it leaves the caret on the current line until the server confirms.

The minimal correct fix for D-02: add a new `InputAction` variant (e.g. `PredictEnter`)
that is returned by `classify_input` for `b"\r"` and `b"\n"`, and handle it in `on_input`
with the following logic:

```rust
InputAction::PredictEnter => {
    // Mirror Mosh newline_carriage_return:
    // 1. become_tentative (new epoch — subsequent chars are hidden until confirmed).
    // 2. Predict cursor → (row+1, 0) if not on last row; (row, 0) with blank-row
    //    prediction if on last row.
    // 3. Clear pending predictions (same as EpochReset — we cannot know if we're
    //    in a noecho prompt until the server confirms the next epoch).
    self.pending.clear();
    self.become_tentative();
    self.cursor_motion_pending = false;
    self.needs_epoch_start_sync = true;

    let current_row = self.predicted_cursor.row;
    if current_row < self.term_rows.saturating_sub(1) {
        // Normal case: advance to next row, column 0.
        self.predicted_cursor = CursorPos { row: current_row + 1, col: 0 };
        self.cursor_motion_pending = true;
    } else {
        // At last row: cursor stays at (row, 0) — scroll is unpredictable.
        // Mosh does NOT predict scroll; we match that.
        self.predicted_cursor = CursorPos { row: current_row, col: 0 };
        self.cursor_motion_pending = true;
    }
}
```

**Why this works within the existing noecho suppression machinery:**
- `become_tentative()` increments `prediction_epoch`.
- The cursor prediction produced by `predicted_cursor()` is gated by `should_display()` and
  returns `None` until `confirmed_epoch` catches up. Since noecho prompts never echo, the
  cursor stays hidden for the entire noecho session — same structural guarantee as the existing
  char predictions.
- The Mosh "blank-row prediction" for the scroll case does not directly apply in our model
  (we have no row-level overlay, only per-cell `PendingPrediction`). For the scroll case, simply
  set cursor to `(row, 0)` with `cursor_motion_pending = true` — the client will see the correct
  confirmed position once the server sends the next epoch. This is equivalent to Mosh's
  "commented out scroll prediction" (intentionally not predicted).

### Noecho regression risk

The key invariant: after `become_tentative()`, `prediction_epoch` > `confirmed_epoch`. The cursor
prediction from `predicted_cursor()` only emits when `has_visible || cursor_motion_pending`.
`cursor_motion_pending` is set by `PredictEnter`. However, `predicted_cursor()` does NOT gate
on tentative state for the cursor — it gates on `should_display()`.

**Critical check:** `should_display()` is currently gated on `srtt_trigger` or `Always` mode.
In Always mode (used in tests), the cursor WILL be shown after the Enter prediction, at
`(row+1, 0)`. This is correct for a non-secret prompt (the user sees the caret jump down).
For `read -s`: the secret characters immediately following will be classified as printable and
enqueued, but with `tentative_until_epoch > confirmed_epoch` — so chars stay hidden. The cursor
prediction at `(row+1, 0)` will be visible briefly until `cull()` sees the confirmed cursor is
on a different row (the server put the prompt there), triggering `reset()`. This matches Mosh
behaviour: Mosh shows the caret at the predicted position and corrects on first confirming diff.

**Test that must not regress:** `noecho_suppression` (unit), `noecho_read_dash_s_zero_predicted_chars`
(integration). These test that chars typed after Enter in noecho mode are not shown — they
remain valid since char predictions are tentative. The cursor prediction visibility is a separate
concern not tested by those tests; add a targeted test.

### Scroll region / alternate screen

When the shell is in an alternate screen (vim, less), `screen.confirmed_cursor().row` reflects
the actual cursor row in the viewport. The `term_rows` field tracks the current terminal height.
No special scroll-region handling is needed for the basic D-02 fix — the case where the cursor
is at the last row and scroll is unpredictable is handled by the else branch above (cursor to
`(row, 0)`, no row advance). This matches Mosh exactly. [ASSUMED — scroll-region DECSTBM is not
tracked in nosh's confirmed state; verify no DECSTBM-aware fix is needed at implementation time]

## Q3: Fast-typing "Letters Disappearing" — Lifecycle & Instrumentation (D-03)

### Root cause hypothesis (confirmed by code read)

**Hypothesis:** during a key-repeat burst (e.g. holding 'j' in vim or mashing the keyboard),
the OS delivers bytes to stdin in batches. If any batch of > 4 bytes contains a non-printable
character (0x0d CR, 0x1b ESC, or any control char), `classify_input` returns `EpochReset` or
`BulkSuppressed`. The `on_input` handler then calls `reset()` or `reset_with_cursor()`, which
calls `pending.clear()` — dropping every already-visible prediction. Letters vanish until the
next confirming datagram (~RTT later). [VERIFIED: predictor.rs:738-821 classify_input logic;
:415-430 EpochReset/BulkSuppressed handlers]

**When this fires during normal fast typing:**
- Typing quickly enough that the OS batches keystrokes: e.g. "jjjjj" + implicit CR if holding
  Enter, or any arrow/function key mixed into the hold burst.
- On some terminal emulators, key-repeat sends the key's escape sequence as a batch alongside
  the preceding chars: e.g. `b"hello\x1b[A"` (hello + up-arrow). This batch fails the
  `all_single_width` check and returns `BulkSuppressed`.

**Mosh does not have this problem** because Mosh processes keystrokes byte-by-byte through its
VT parser (`parser.input(the_byte, actions)`) and each byte produces an action. There is no
batch suppression in Mosh's model; our `BULK_SUPPRESS_THRESHOLD` is a nosh-specific design
choice that traded accuracy for complexity. The fix is to avoid calling `reset()` when the batch
is a printable-only fast-repeat sequence, or to tighten the classification so short pure-printable
bursts don't mis-classify.

**Secondary hypothesis:** the `EpochReset` path for `b"\r"` (Enter) is triggered mid-burst if
the OS delivers `"jjj\r"` as one read. This is less likely during typematic (the user is holding
a letter key, not Enter) but possible during fast mashing. Instrumentation will distinguish.

### Instrumentation design for D-03

The tracing event must capture, per `on_input` call:

```rust
// In on_input, immediately after classify_input returns `action`:
tracing::debug!(
    target: "nosh::predict",
    event = "on_input",
    batch_len = bytes.len(),                       // raw byte count
    action = ?action,                              // full Debug repr (no char content for security)
    pending_before = self.pending.len(),           // how many predictions were queued
    // pending_after is captured after the match arm runs — log it with a second event
    // or restructure as a single event after the match (see below)
);
```

Because `action` carries the `InputAction` enum, its `Debug` output will show `EpochReset`,
`BulkSuppressed`, `PredictBatch([(_, _), ...])` (char count visible but no content), `PredictChar`
etc. This avoids logging character content (T-15-08 security requirement).

A cleaner approach: log a single event AFTER the `match action` block, using local variables set
inside each arm:

```rust
let pending_before = self.pending.len();
let action_kind = action_kind_tag(&action); // e.g. "EpochReset", "BulkSuppressed", "PredictChar"

match action {
    // ... existing arms, each arm sets `dropped = pending_before - self.pending.len()` or similar
}

tracing::debug!(
    target: "nosh::predict",
    event = "on_input",
    batch_len = bytes.len(),
    action = action_kind,
    pending_before,
    pending_after = self.pending.len(),
    // Number of predictions cleared by this call (nonzero = a reset happened):
    predictions_dropped = pending_before.saturating_sub(self.pending.len()),
    predicted_cursor_col = self.predicted_cursor.col,
    predicted_cursor_row = self.predicted_cursor.row,
);
```

This gives the operator:
- Which arm fired for each batch (action_kind).
- How many pending predictions were lost per call (predictions_dropped > 0 = "letters disappeared
  here").
- The predicted cursor position after the call.

A helper `fn action_kind_tag(a: &InputAction) -> &'static str` avoids logging char content:

```rust
fn action_kind_tag(a: &InputAction) -> &'static str {
    match a {
        InputAction::PredictChar { .. } => "PredictChar",
        InputAction::PredictBatch(v) => if v.len() > 1 { "PredictBatch" } else { "PredictChar" },
        InputAction::PredictBackspace => "PredictBackspace",
        InputAction::PredictCursorLeft => "PredictCursorLeft",
        InputAction::PredictCursorRight => "PredictCursorRight",
        InputAction::PredictLineStart => "PredictLineStart",
        InputAction::PredictLineEnd => "PredictLineEnd",
        InputAction::EpochReset => "EpochReset",
        InputAction::BulkSuppressed => "BulkSuppressed",
        InputAction::BracketedPasteStart => "BracketedPasteStart",
        InputAction::BracketedPasteEnd => "BracketedPasteEnd",
    }
}
```

### Where to add the instrumentation

`on_input` is in `predictor.rs`. The existing `tracing::debug!` in `main.rs:1223` is the
keystroke-level latency log (one event per batch forwarded to server). The D-03 decision-trace
should live in `predictor.rs:on_input` — closer to the mutation — not in `main.rs`. The existing
`main.rs` log can grow a `pending_after = predictor.pending_len()` field to cross-reference
without adding a second log point in main.

### Hypothesis fix

Once the trace confirms the mid-burst-reset theory, the fix is to split `BulkSuppressed` into
two outcomes:

1. **Printable-only bulk** (already handled as `PredictBatch`) — no change needed.
2. **Mixed or non-UTF-8 bulk** — currently `BulkSuppressed` → `reset()`.

The hypothesis fix: if `pending.len() > 0` at the time of a `BulkSuppressed` classification
(predictions are already being shown), do NOT call `reset()` — call `become_tentative()`
instead (increment epoch, mark new predictions as tentative, but do not clear existing ones).
The existing `cull()` will remove them on the next datagram if they mismatch.

**Risk:** this could leave stale predictions visible longer (until the next confirming datagram)
in edge cases where the server did something unexpected mid-burst. That is the same trade-off
Mosh accepts — it only resets on a confirmed mismatch from `cull()`, not proactively on ambiguous
input.

**Test shape (fail-before/pass-after):**
```rust
#[test]
fn bulk_suppressed_does_not_drop_existing_predictions() {
    // Setup: one confirmed printable prediction in pending.
    // Action: on_input with a BulkSuppressed batch.
    // Assert (before fix): pending.len() == 0 (letters disappeared).
    // Assert (after fix): pending.len() == 1 (existing prediction preserved).
}
```

### Mosh comparison: why our model is different

Mosh calls `cull(fb)` at the START of every `new_user_byte`. This means before enqueuing any new
prediction, Mosh reconciles against the current confirmed screen. Our model cannot do this because
we only have the confirmed screen state when a datagram arrives (the `screen.apply(diff)` +
`cull()` in the datagram arm). During the typing interval between datagrams, we have no fresh
confirmed state to cull against — so we cannot do Mosh's "cull before every keystroke" pattern.
This is a fundamental structural difference, not a bug. The instrumentation will tell us which
reset path actually fires during the typematic glitch.

## Architecture Patterns

The D-01, D-02, and D-03 changes are independent:

- **D-01** modifies only the `diff_interval.tick()` arm in `session_pump` (`server.rs`) —
  the single-datagram call becomes a loop. No changes to `build_state_diff` signature or
  `transport.rs`.

- **D-02** requires adding `InputAction::PredictEnter` to `predictor.rs:InputAction` and
  updating `classify_input` to return it for `b"\r"` and `b"\n"`. The `EpochReset` arm
  continues to handle Tab, ESC, and other control chars. The `PredictEnter` arm in `on_input`
  implements the cursor-advance logic.

- **D-03** adds tracing in `predictor.rs:on_input` (decision-trace event) and the
  hypothesis fix modifies the `BulkSuppressed` arm.

### Anti-Patterns to Avoid

- **D-01:** Do NOT check `conn.rtt()` or internal congestion state as a proxy for budget.
  `datagram_send_buffer_space()` is the only stable, correct proxy.
- **D-01:** Do NOT use `send_datagram_wait` — it serialises across tick boundaries.
- **D-02:** Do NOT add an explicit "noecho mode" flag. The existing tentative/epoch machinery
  already handles suppression structurally. Adding a flag duplicates the invariant and creates
  a divergence risk.
- **D-03:** Do NOT log character content in any tracing event. `action_kind_tag` must not
  include `ch` or batch content (T-15-08).

## Common Pitfalls

### Pitfall 1: `datagram_send_buffer_space` not on `quinn::Connection` public API

**What goes wrong:** the method exists on `quinn_proto::connection::Datagrams` (the internal
type) and may or may not be exposed on `quinn::Connection` (the public type). The docs.rs page
confirmed it exists, but confirm the exact call site before writing the loop.

**How to avoid:** check `docs.rs/quinn/0.11.9/quinn/struct.Connection.html#method.datagram_send_buffer_space`
before writing the burst loop. If the method is missing from the public type, use a byte count
cap (e.g. `max_datagrams_per_tick = 32`) as the fallback.

**Warning signs:** compile error `no method named datagram_send_buffer_space on quinn::Connection`.

### Pitfall 2: `build_state_diff` epoch increments on each call

`build_state_diff` increments `current_epoch` when the grid changed since the last sent
snapshot or deferred runs exist. Calling it in a loop without advancing `last_sent_snapshot`
between iterations would increment the epoch on every call even when the grid hasn't changed,
creating spurious epochs. The loop must use `result.sent_cells` to update `last_sent_snapshot`
on each iteration so the next call sees the correct baseline. [The sketch above does this
correctly.]

### Pitfall 3: `PredictEnter` cursor prediction visible in noecho epoch

After `PredictEnter`, `cursor_motion_pending = true`. `predicted_cursor()` returns `Some` when
`cursor_motion_pending && should_display()`. Under Always mode in tests, this shows the cursor
at `(row+1, 0)` immediately — which is CORRECT for an echoing prompt. In a noecho session, the
server will send a confirming diff without the expected row advance, triggering `cull()` to call
`reset()` (non-tentative cursor mismatch). This is the correct self-healing path. The existing
`noecho_suppression` test does not assert on cursor position, so it will not regress; add a
new test specifically for the cursor prediction in PredictEnter.

### Pitfall 4: `classify_input` Enter handling split breaks existing tests

The existing tests `classify_enter_epoch_reset` assert that `b"\r"` → `EpochReset`. Changing
`b"\r"` to return `PredictEnter` will break those tests. The tests must be updated to assert
`PredictEnter`, and the test name updated. This is intentional — the change in classification is
the point.

### Pitfall 5: D-03 hypothesis fix allows tentative stale predictions past RTT

If `BulkSuppressed` calls `become_tentative()` instead of `reset()`, predictions from before
the bulk event remain in `pending` with the old epoch. They are tentative (hidden) if
`tentative_until_epoch > confirmed_epoch`. On the next `cull()` they will be matched against the
confirmed grid. If the grid matches, they confirm and `confirmed_epoch` advances. If not, the
non-tentative path fires `reset()`. Net effect: at worst, a stale prediction survives until the
next datagram (RTT) instead of being cleared at keystroke time. This is the same RTT-bounded
latency the tentative mechanism already accepts.

### D-01: Burst loop skeleton

```rust
// diff_interval.tick() arm — server.rs:676-712 replacement
_ = diff_interval.tick() => {
    if !resume_complete {
        continue;
    }
    let cap = match conn.max_datagram_size() {
        Some(c) if c >= MIN_CAP => c,
        _ => continue,
    };

    loop {
        // Budget gate: stop if Layer 1 queue < one datagram free.
        // datagram_send_buffer_space() is confirmed on quinn::Connection 0.11.9.
        // Verify method name at impl time (see Pitfall 1).
        if conn.datagram_send_buffer_space() < cap {
            break;
        }

        let deferred = std::mem::take(&mut pending_deferred);
        match build_state_diff(
            &slot, &mut current_epoch, last_acked_epoch,
            &last_acked_snapshot, &last_sent_snapshot, deferred, cap,
        ) {
            None => break,
            Some(result) => {
                epoch_snapshots.push_back((result.epoch, result.sent_cells.clone()));
                if epoch_snapshots.len() > EPOCH_SNAPSHOT_CAP {
                    epoch_snapshots.pop_front();
                }
                last_sent_snapshot = result.sent_cells;
                let no_more = result.deferred.is_empty();
                pending_deferred = result.deferred;

                if let Err(e) = conn.send_datagram(result.payload) {
                    use quinn::SendDatagramError::*;
                    match e {
                        TooLarge => {}
                        UnsupportedByPeer | Disabled | ConnectionLost(_) => {
                            // break SessionEnd::TransportLost — caller handles
                        }
                    }
                }

                if no_more { break; }
            }
        }
    }
}
```

## Open Questions (RESOLVED)

1. **`build_state_diff` deferred-only call in burst loop**
   - What we know: when `deferred` is empty and the grid hasn't changed, `build_state_diff`
     returns `None`. The loop breaks on `None`.
   - What's unclear: if the grid DID change between tick iterations (PTY output arriving on
     `out_rx.recv()` while the burst loop is running in the same `select!` arm), the second
     loop iteration will compute a fresh diff. This is correct — but in the `tokio::select!`
     model, the `diff_interval.tick()` arm runs to completion before returning to the select
     loop. Multiple PTY chunks won't interleave within one tick arm. No issue.

2. **`PredictEnter` cursor visibility test coverage**
   - What we know: existing noecho tests assert zero char predictions shown; they do not assert
     cursor position.
   - What's unclear: whether a new test is needed to assert that the cursor IS at `(row+1, 0)`
     after `PredictEnter` in non-noecho mode (Always display).
   - Recommendation: add one test `enter_predicts_line_advance_cursor` and one
     `enter_at_last_row_stays_on_row`.
