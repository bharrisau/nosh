<objective>
Replace the single-datagram-per-tick send in both server tick arms with a burst loop that drains a full state diff within one tick, so full-screen repaints land in roughly one RTT instead of dribbling one MTU per 16 ms tick.

Purpose: Implements PACE-01 (burst until send budget exhausted) and PACE-03 (no R-1 infinite spin; one build_state_diff per tick; encode_datagram-only drain), while preserving the PACE-02 epoch invariant (D-20-04: exactly one epoch per tick). This is the redo of the reverted 999.4 attempt with both failure modes (R-1 spin, R-2 noecho-epoch) designed out architecturally.
Output: Extended `DiffTickResult`, a `send_burst()` free function called from both tick arms, and two RED-before/GREEN-after unit tests gating the design.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server tick loop → QUIC datagram channel | Server-generated terminal state crosses to the wire; the rate/epoch of these datagrams determines what the client treats as "confirmed" |
| server send budget → unauthenticated/congested path | A pathological diff could try to monopolise the send buffer in one tick |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-01 | Info Disclosure | burst loop epoch assignment (server.rs send_burst) | mitigate | D-20-04 one epoch per tick: send_burst reuses `result.epoch` for every burst datagram and never calls build_state_diff (the only thing that increments current_epoch). This prevents `confirmed_epoch` from advancing during a `read -s` noecho window — the R-2 attack where an observer of predicted password chars could read leaked echo. The structural proof is the `noecho_read_dash_s_zero_predicted_chars` CI gate (owned by plan 20-02, D-20-09) which must pass with this burst code active. |
| T-20-02 | Denial of Service | burst loop send budget (server.rs) | mitigate | D-20-01/D-20-02: `datagram_send_buffer_space() >= cap` per-iteration gate plus `BURST_CAP = 64` bound a pathological diff (huge paste, oversized terminal) from monopolising the send buffer in one tick (~64 x 1200 ≈ 76 KB, well within the default 1 MiB buffer). |
| T-20-03 | Denial of Service | R-1 infinite spin (server.rs send_burst) | mitigate | D-20-03: drain is `encode_datagram`-only; build_state_diff is never called inside the loop, so `fresh_runs` is not recomputed against a non-advancing `last_acked_snapshot`. The `burst_drains_when_grid_differs_from_acked_baseline` test (plan 20-01 Task 1) asserts finite termination. Without this, a single session task pegs a CPU core. |
| T-20-04 | Resource Exhaustion | epoch_snapshots store (server.rs) | mitigate | D-20-04 keeps one epoch per tick → one `epoch_snapshots.push_back` per tick, unchanged from pre-burst; EPOCH_SNAPSHOT_CAP=16 eviction is not stressed by burst size (Pitfall 5). |
| T-20-SC | Tampering | npm/pip/cargo installs | n/a | Phase 20 installs no packages; no Cargo.toml change. No legitimacy gate required. |
</threat_model>
