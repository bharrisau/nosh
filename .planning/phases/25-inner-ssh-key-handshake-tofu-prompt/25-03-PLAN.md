<objective>
Implement the client side of the WebTransport inner SSH-key handshake plus the SEC-02 TOFU prompt. Add `run_inner_auth_client` (verifies the server EKM binding, runs the blocking TOFU prompt for an unknown server key, signs the EKM-bound transcript, verifies the server's completion signature), wire it into the WT connect path before the session pump, and replace the native-path silent-record TOFU in `HostKeyVerifier` with a `TofuPolicy` that prompts interactively and fails closed on no-TTY (D-08/D-09/D-10).

Purpose: the client half of mutual auth + the user-facing security control. The TOFU prompt is what makes a first-contact MITM detectable; failing closed on no-TTY prevents silent trust in automation. Inner auth runs only on the WebTransport path (D-02) — the native QUIC path keeps its proven TLS-handshake auth, changing only how an unknown host key is handled.
Output: `run_inner_auth_client` returning the authenticated control stream pair; WT connect-path wiring; `TofuPolicy` (Silent/Interactive/TrustKey) on `HostKeyVerifier` with an interactive `prompt_and_record` and no-TTY fail-closed; `sha2`+`getrandom` (real dep) on nosh-client.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server control stream → client | Untrusted server frames (challenge/complete) cross here; a relaying proxy is a potential MITM |
| Unknown host key → user trust decision | First-contact TOFU is the only human-in-the-loop control against a first-connection MITM |
| Non-interactive context → trust | Automation with no TTY must not be silently trusted into accepting a new key |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-03-WT3 | Spoofing | EKM binding check | mitigate | Client asserts `ekm_from_server == locally_derived_ekm` before signing; a proxy on a different TLS leg has a different EKM → client refuses before producing a signature (Task 1 step 4) |
| T-25-03-SEC3 | Spoofing | TOFU fatigue / auto-accept | mitigate | Blocking prompt, explicit `yes` required, empty input = no, decline disconnects cleanly; `prompt_tofu_rejects_empty_input` test guards the parse (D-08) |
| T-25-03-NOTTY | Spoofing | no-TTY silent trust | mitigate | `is_terminal()` gate fails closed on both the WT (inner_auth.rs) and native (verifier.rs) paths; prints fingerprint + future `--trust-key` reference, never records (D-10) |
| T-25-03-MISMATCH | Spoofing | known_hosts pin violation | mitigate | A `Some(known)` that differs from the presented/server key is a hard fatal error (no prompt) on both paths — preserves the v1.x MITM-detection behaviour |

| T-25-03-SC | Tampering | cargo installs (sha2, getrandom) | accept | Promoting an existing dev-dep + adding an already-vetted RustCrypto crate; RESEARCH Package Legitimacy Audit: no new external packages |
